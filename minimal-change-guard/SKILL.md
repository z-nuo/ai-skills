# 最小改动范围检查

检查可以覆盖完整调用链；写入必须对应用户需求。最小改动是完成需求所需的完整变更，不以文件数或行数代替正确性判断。

只读审查时，以下写入、撤销和验证修复步骤转为提出发现与建议，不修改文件。

## 修改前：建立范围基线

1. 阅读适用的仓库规则和目标调用链，用一句话复述验收目标。区分用户明确要求、代码已证明的事实和待确认的假设。
2. 检查当前工作树，记录已有的暂存、未暂存和未跟踪改动。后续以本次实际写入为依据区分来源，不能把全部 `git diff` 当作自己的修改。
3. 简述计划修改的文件及各自对应的需求。简单任务用一两句话即可，不另建计划文档；已经授权且需求明确的工作直接继续，不增加重复审批。

## 修改中：判断每处变更的必要性

每个修改块至少满足以下一项：

- **直接需求**：能指出它实现了用户的哪条要求。
- **必要连带变更**：由已授权的直接变更引起，为保持其余既有契约而必须完成的适配。说明“哪项直接变更 → 哪个调用或契约会失效 → 为什么此处必须修改”。修改签名、字段或调用点只是适配形式，不能单独作为必要性依据。例如删除方法时同步处理仍调用它的入口。

涉及数据来源、保护或防重机制、读写路径、查询与发奖关系的变化，先核对是否已由用户需求或本轮已确认方案覆盖。已覆盖的直接执行；未覆盖的变化不能以“机械适配”为由实施。若完成需求必须作出尚未授权的业务选择，说明具体影响，仅暂停依赖该选择的部分并询问。

如果两项都不满足，保留原样。搜索命中、风格统一、未来可能有用，以及“测试已经写了”，都不是修改依据。

- 优先在现有职责内直接表达规则。少量条件判断不自动需要 helper、新配置项或新抽象。
- 保持未涉及代码的格式、方法顺序、注释和环境配置。文档或目录更新只覆盖用户明确要求或仓库维护约定要求的部分。
- 用户要求移除旧逻辑时，删除必要的定义和调用；不要擅自将旧入口接到新流程，也不要自行增加历史回读、双写或数据迁移。
- 如果按要求修改会破坏现有鉴权、防重复发奖等保护，说明具体路径及后果。明确范围内的必要修正继续执行；必须新增业务策略或违背用户明确约束时，提出一个决定性问题，仅暂停依赖该答案的部分。等待期间保留这些路径所需的定义和保护，不提前拆除依赖。
- 不因减少 diff 而遗漏必要调用方、不保留失效调用，也不在用户要求“删除逻辑”后留下无意义的空方法。
- 测试预期来自用户要求和既有契约，不来自自行扩展的实现；用测试证明用户没要求的行为，等于把扩展合理化。
- 测试应对应用户需求、受影响的既有契约或已证明的回归风险。优先复用现有验证手段；缺少测试设施时，可使用不进入交付补丁的临时脚本或最小替身验证必要行为。新增持久化测试设施或依赖须有具体必要性依据，不为满足流程而引入；在交付时写明实际运行的命令。

## 用户纠正方向：重新审查整个补丁

先用一句话说明纠正后的目标，然后核对本次已经修改的全部文件，撤销自己的错误实现及其附带测试、注释、配置和格式变化。不能只修用户点名的那一行就宣布完成。

撤销以修改来源为边界：保留用户和其他协作者的改动。重读文件确认是否出现新变化；混合修改按块处理。无法确定来源时先保留并说明，不整文件恢复到 `HEAD`，不使用破坏性重置。

## 完成前：逐块对照验收目标

检查本次完整 diff，包括新文件和暂存区。为每个修改块匹配“直接需求”或“必要连带变更”，移除自己的无依据改动，再完成项目规定的验证。

交付时简要说明：

- 实际修改文件及对应需求；必要连带变更附具体原因。
- 实际运行的验证及结果；外部服务等未覆盖边界。
- 尚未解决的范围决策或已发现的相关风险。

测试通过不能替代范围验收。未运行的验证不写成通过；仅作静态检查不声称线上可用。

## 边界示例

用户要求“移除旧奖励锁；新锁仅在指定时间后将 section 固定为 0”。必要修改是删除旧锁定义、方法及调用，并在新锁现有字段生成位置加入时间判断。若旧领取入口会因此失去防重保护，应说明并确定入口处置；不能自行改成复用新锁。仅用于说明旧 key 的配置枚举注释不构成功能依赖，不因检索命中而改写。

本技能约束任务范围，不授予提交、推送、部署或修改外部系统的权限。只读审查只输出发现；用户要求修正时才实施相应修改。可与实现、测试和代码审查技能配合，但不要求额外安装或固定组合。
