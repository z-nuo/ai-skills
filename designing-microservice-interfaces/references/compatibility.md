## 基本原则

- 所有可观察行为都可能已被消费者依赖，包括错误、排序、默认值、延迟和未记录的兼容行为。
- “schema 能解析”只证明部分线兼容，不代表源代码兼容、行为兼容或业务兼容。
- 优先在同一代契约上做加法演进，不把新版本当作修改已有语义的捷径。
- 没有可用替代方案、迁移说明和消费者观测时，不开始强制弃用。
- 接口生产方负责推动迁移或提供兼容层，不能只发布通知后把成本转嫁给消费者。

## 消费者盘点

在判断兼容性前建立消费者清单：

1. 搜索代码仓库、生成 SDK、网关、任务脚本、移动端和第三方集成中的调用。
2. 使用访问日志、RPC 指标、client metadata、API key 或调用方标签确认真实流量。
3. 记录消费者所有者、环境、调用量、客户端版本、升级窗口和关键依赖行为。
4. 标记无法识别的流量和仓库外消费者；存在未知消费者时，不声称变更安全。
5. 保存变更前基线，包括成功率、错误分布、延迟和旧接口使用量。

## 变更分类

### REST/OpenAPI

| 变更 | 默认判断 | 需要额外检查 |
|---|---|---|
| 增加可选请求字段 | 通常兼容 | 服务端默认行为是否保持不变 |
| 增加响应字段 | 通常兼容 | 严格反序列化、签名或缓存键 |
| 增加 enum 值 | 潜在破坏 | 消费者是否使用穷举分支 |
| 增加必填请求字段 | 破坏性 | 是否存在兼容默认值或过渡期 |
| 删除、改名或改变字段类型 | 破坏性 | 是否能通过双字段和适配器过渡 |
| 改变状态码、错误 code、排序或空值语义 | 行为破坏 | schema diff 可能无法发现 |
| 收紧校验、权限或限流 | 潜在破坏 | 现有合法流量是否会被拒绝 |

### gRPC/Protobuf

| 变更 | 默认判断 | 需要额外检查 |
|---|---|---|
| 使用新编号增加字段 | 通常线兼容 | 默认值、生成代码和业务行为 |
| 增加 enum 值 | 线兼容但可能源代码破坏 | Go/PHP 未知值处理和穷举逻辑 |
| 删除字段并 `reserved` | 旧客户端通常可解析 | 数据丢失和业务依赖 |
| 复用 field number | 禁止 | 可能把旧数据解析成新语义 |
| 改变字段类型、编号、package 或 RPC 形态 | 破坏性 | 必须引入替代契约和迁移 |
| 改变 status code、默认值、排序或副作用 | 行为破坏 | `buf breaking` 不一定发现 |

兼容性结论必须分别说明线格式、源代码和行为三个维度。

## 迁移流程

### 1. 建立旧契约基线

保存当前 OpenAPI/descriptor、示例、契约测试和真实流量行为。不要只根据最新代码推断旧消费者看到的契约。

### 2. 设计替代契约

替代接口覆盖所有关键用例，并修复边界问题。定义新旧字段、操作、错误和权限之间的明确映射。

### 3. 自动检测差异

REST 使用仓库已有 OpenAPI diff 工具并人工检查行为变化；gRPC 使用 `buf breaking` 或 descriptor diff。工具结果是输入，不是最终兼容性结论。

### 4. 提供过渡机制

选择适配器、双字段、网关转换、并行 RPC 或渐进路由。明确过渡期内哪个契约是事实来源，避免新旧接口互相漂移。

### 5. 逐个迁移消费者

为每个消费者执行修改、契约测试、集成验证、灰度放量和使用量确认。高风险消费者单独设置回滚点。

### 6. 移除旧接口

只有在生产指标显示零有效调用、未知流量已处理、回滚窗口结束后，才删除旧契约、实现、配置、测试和文档。

## 过渡模式

- **加法扩展**：新增可选字段或新 RPC，旧契约保持有效。默认首选。
- **双字段迁移**：短期同时接受旧字段和新字段，响应保持稳定，并观测旧字段使用量。
- **适配器**：旧接口转换为新实现，让消费者按自己的节奏迁移。
- **Strangler/Gateway**：按消费者或流量比例把调用逐步切换到新接口。
- **影子请求**：将生产请求复制到新实现比较结果，但禁止影子路径产生业务副作用。

过渡机制必须有删除日期或可度量的退出条件，不能永久保留两套接口。

## 弃用说明

每份弃用说明至少包含：

- 被弃用的路径、operation、service/RPC、字段或行为。
- 推荐替代方案及完整契约链接。
- 弃用原因、负责人、开始时间和预计移除时间。
- 消费者需要执行的步骤、示例和验证命令。
- 兼容层行为、已知差异、支持渠道和回滚方式。
- 旧接口使用量仪表盘或可验证的完成标准。

默认使用建议性弃用。只有安全风险、维护成本或演进阻塞足够明确，并且迁移工具和支持已就绪时，才使用强制截止日期。

## 发布、观测与回滚

- 先部署兼容生产者，再升级消费者；不要让消费者依赖尚未部署的契约。
- 使用 canary 或按消费者灰度，观察成功率、错误 code/status、延迟、重试和旧接口调用量。
- 定义自动或人工停止条件，例如错误率、业务不一致或未知调用方增加。
- 回滚必须恢复旧消费者仍可使用的契约和行为；数据库或不可逆副作用需要单独方案。
- 在灰度窗口内保留旧路径和必要的兼容数据，不在同一次发布中立即删除。

## 评审输出

兼容性评审按以下顺序输出：

1. 结论：兼容、潜在破坏或破坏性，并区分线格式、源代码和行为。
2. 证据：契约差异、消费者清单、调用指标和工具结果。
3. 受影响消费者：负责人、版本、风险和迁移成本。
4. 迁移步骤：生产者、消费者和流量切换顺序。
5. 观测与回滚：指标、停止条件、恢复路径。
6. 移除门槛：零使用量、回滚窗口和清理范围。

## 完成条件

- 替代接口已在生产验证并覆盖关键用例。
- 所有已知消费者完成迁移，未知流量为零。
- 契约测试、OpenAPI/Protobuf breaking check 和集成验证通过。
- 旧接口生产使用量在约定观察期内持续为零。
- 旧契约、实现、配置、测试和文档已完整移除。
