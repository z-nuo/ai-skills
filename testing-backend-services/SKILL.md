# 后端服务测试

## 核心目标

用最小且可信的自动化测试证明后端行为。测试真实可观察结果而不是实现细节或 mock 调用次数，并用实际失败与通过结果说明测试具有检测能力。

## 核心原则

- 新功能、缺陷修复和行为变更遵循 RED -> GREEN -> REFACTOR；没有看到预期失败，不进入实现。
- 既有行为补覆盖使用特征测试，并通过已知反例、旧版本或受控变异证明断言具有敏感性，不伪造 RED。
- 选择能够证明风险的最小边界：纯逻辑用单元测试，基础设施适配用集成测试，公共接口用 API/契约测试。
- 优先测试真实行为。只在不可控、昂贵或不稳定的外部边界使用最小 test double。
- 测试必须确定、隔离、可重复运行；禁止依赖执行顺序、固定 sleep、共享脏数据或本机隐式状态。
- 覆盖率用于发现盲区，不作为替代行为断言的目标。

## 工作流

### 1. 检查仓库

阅读现有测试、`go.mod`、`composer.json`、Makefile、测试配置、容器配置和 CI。先使用仓库已有框架、断言库、fixture、factory、命令和目录结构。

查明被测行为、依赖边界、测试数据库策略和完整测试命令。不要未经用户允许安装新依赖或更换测试框架。

### 2. 分类任务

- **新行为或缺陷**：先编写一个最小测试并运行，确认因目标行为缺失而失败，而不是语法、环境或 fixture 错误。
- **既有行为补覆盖**：先记录当前契约，编写特征测试，再用已知反例、旧修订或可恢复的受控变异验证测试会在行为改变时失败。
- **测试评审**：先按严重程度列出测试空洞、错误断言、过度 mock、非确定性和隔离问题，再给修复建议。

### 3. 建立测试边界矩阵

| 层级 | 证明内容 | 默认边界 |
|---|---|---|
| 单元测试 | 领域规则、校验、状态转换和错误分支 | 进程内，不访问网络或真实基础设施 |
| 集成测试 | Repository、数据库、Redis、消息适配器及序列化 | 真实依赖，优先 Testcontainers |
| API/契约测试 | HTTP/gRPC 输入输出、状态、错误、鉴权和兼容契约 | 从传输边界调用真实应用组件 |

只测试该层负责的风险。不要在单元测试重复 ORM 行为，也不要用端到端路径替代可快速定位的领域测试。

### 4. 加载对应参考

- Go 代码读取 [references/go.md](references/go.md)。
- PHP 代码读取 [references/php.md](references/php.md)。
- 需要数据库、Redis、消息系统或其他容器依赖时读取 [references/integration.md](references/integration.md)。
- 公共 REST/gRPC 契约缺失或需要修改时，**REQUIRED SUB-SKILL:** Use designing-microservice-interfaces。已有契约的验证不重复设计接口。

### 5. 设计用例

从业务契约推导成功、边界、错误和副作用用例。优先覆盖高风险分支、事务边界、幂等、权限、并发、重试和序列化，而不是机械枚举每个函数。

每个测试名称描述场景和结果；Arrange/Act/Assert 保持可辨认。fixture 只包含当前行为需要的数据，通用构造器不得隐藏关键前置条件。

### 6. 执行 RED/GREEN

先运行最小测试范围并读取完整失败：

1. 确认测试失败而不是环境报错。
2. 确认失败信息指向预期行为。
3. 实现或修复最小代码使其通过。
4. 重跑同一测试并确认输出干净。
5. 重构后再次运行相关测试。

本技能只在用户请求实现行为时修改生产代码；仅要求补测试或评审时，不借机改变业务逻辑。

### 7. 扩大验证范围

最小测试通过后，运行所属 package/module、相关集成测试，再按仓库成本运行完整测试集、race/static checks 或 CI 等价命令。任何未运行项都要说明原因，不能从局部通过推断全局通过。

## API 与契约测试

- REST 从 HTTP 边界发起请求，验证状态码、headers、响应 schema、错误结构、鉴权、幂等和分页。
- gRPC 使用生成 client 或 in-process transport，验证 status、details、deadline、metadata 和消息兼容性。
- 契约测试以仓库中的 OpenAPI/Protobuf 为事实来源；发现契约与实现不一致时明确指出哪一方需要变更。
- 不把 handler/service 全部 mock 后称为 API 测试。

## 默认交付物

按以下顺序输出：

1. **测试目标与假设**：目标行为、风险、已有工具和未确认约束。
2. **测试边界与用例矩阵**：每个用例所属层级及其证明内容。
3. **测试代码与环境**：新增或修改文件、fixture、容器和迁移准备。
4. **RED 证据**：命令、预期失败及失败原因；特征测试说明敏感性验证方式。
5. **GREEN 证据**：同一测试及扩大测试范围的实际运行结果。
6. **剩余风险**：未覆盖行为、未运行命令和环境限制。

评审模式将发现的问题置于最前，按严重程度排序并引用测试文件及测试名称；没有问题时说明验证缺口。

## 示例触发

用户提出“为 Go 订单服务补充 MySQL Repository 和创建订单接口测试”时，先拆分领域、Repository 和 HTTP 边界，使用真实数据库容器验证持久化，用 `httptest` 验证 HTTP 契约，并分别记录最小测试与相关测试集结果。

## 红线

- 不断言 mock 本身存在或被调用来替代业务结果。
- 不向生产类型添加只供测试调用的方法。
- 不在不了解副作用时 mock 高层依赖。
- 不使用固定 sleep 等待容器、异步任务或最终一致性。
- 不让集成测试依赖共享测试环境中的历史数据。
- 不声称测试通过，除非本轮实际运行了对应命令并检查退出状态。
