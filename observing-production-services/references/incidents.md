## 目标与安全边界

事故响应的目标依次是：确认用户影响、控制影响扩大、用证据验证关键假设、恢复服务并验证稳定、最后解释原因和补齐系统缺口。速度不能替代证据，单一相关信号不能证明因果。

线上默认只读。优先读取已有日志、指标、Trace、发布记录、配置版本、依赖状态和运行元数据。以下动作都可能改变现场或扩大影响，必须先取得明确授权：

- 修改配置、发布或回滚版本；
- 扩容、缩容、切换流量或降级功能；
- 重启进程或实例、执行 `kill`；
- 清队列、丢弃消息或重放消息；
- 执行可能增加 CPU、内存、磁盘、网络或依赖负载的高负载查询。

授权必须指向具体动作、目标、范围、执行人和有效时间，不能用笼统的“可以处理”代替。动作前保留必要现场，并记录预期效果、风险、停止条件、回滚条件和验证信号。没有授权时，只输出建议和所需授权，不执行动作。

Kubernetes 仅作为运行证据来源，例如 Pod 状态、重启次数、调度时间、镜像版本和 resource request/limit。Pod 重启或 Pending 只能说明运行状态变化，不能单独证明应用根因；不得把事故分诊扩展为集群、网络插件、调度器或控制面的运维操作。

## 影响摘要与恢复标准

先写影响，再看组件。事故摘要必须区分已确认事实、估算和未知项，并包含：

| 字段 | 要求 |
|---|---|
| 影响范围 | 受影响的用户、租户、地域、入口、业务路径、请求或消息比例；注明统计口径 |
| 开始时间 | 最早用户症状、最早异常信号和确认时间；不确定时给出区间 |
| 当前状态 | 扩大、稳定、缓解、临时恢复、已恢复或仍在观察 |
| 用户症状 | 超时、错误、数据延迟、功能不可用或结果异常，避免只写内部组件症状 |
| 业务影响 | 成功率、订单/任务/消息量、收入或关键流程影响；未知时明确标记 |
| 恢复标准 | 达标信号、阈值或基线、覆盖范围和必须持续的观察窗口 |
| 负责人 | Incident Commander、调查负责人、操作执行人和沟通负责人 |

恢复标准应在采取止损前确定。它至少覆盖用户可见错误率和延迟，并按系统形态补充吞吐、饱和度、积压及数据正确性。不能把“告警恢复”“Pod Running”或单个采样点正常直接当作恢复。

## 事件时间线

统一使用带时区的绝对时间。每条记录包含时间、事件、证据来源、影响判断和置信度；未知时间不要补写。先记录事实，再记录当时作出的决定。

| 时间 | 类型 | 事件或信号 | 证据来源 | 与影响的关系 | 置信度 |
|---|---|---|---|---|---|
| YYYY-MM-DD HH:MM:SS TZ | 发布/配置/流量/依赖/资源/错误/操作 |  |  | 相关、支持因果、反证或待确认 | 高/中/低 |

时间线至少核对以下事件，并将它们对齐到同一异常窗口：

1. **发布**：版本、镜像、feature flag、schema 或依赖包变化，以及灰度和回滚时间。
2. **配置**：配置版本、动态配置、限额、超时、重试、连接池和路由变化。
3. **流量**：请求或消息速率、入口分布、租户/地域/operation 构成和突发变化。
4. **依赖**：下游错误、延迟、限流、连接异常和状态公告；依赖异常仍需证明传播路径。
5. **资源**：CPU、内存、GC、线程或 goroutine、连接、磁盘、网络和队列饱和度。
6. **错误**：用户错误率、异常类型、超时、取消、重试放大和数据一致性症状。
7. **响应动作**：授权、执行、预期效果、实际信号、停止或回滚时间。

时间相邻只表示相关。要支持因果，需证明变化发生在症状之前、覆盖受影响范围、机制能够解释症状，且止损或反事实证据与该机制一致。

## 只读优先的分诊顺序

保持固定窗口、固定口径和小查询范围，按以下顺序推进：

1. **确认影响**：从用户路径和 SLI 判断是否为真实事故，确定范围、开始时间、当前状态和恢复标准。
2. **固定窗口**：选择异常前基线、异常窗口和当前窗口，统一时区、聚合周期和过滤条件。
3. **读取变更**：查看发布、配置和流量记录，不回滚、不修改，先验证时间与影响范围是否吻合。
4. **关联信号**：按同一 service、operation、version、instance、dependency 或 consumer group 对齐日志、指标和 Trace。
5. **检查运行证据**：查看进程/实例状态、重启、资源、队列和连接；Kubernetes 证据只说明运行环境事实。
6. **形成假设**：从已确认事实提出可证伪假设，写出支持证据、反证/缺口和最小下一检查。
7. **逐一验证**：每次只验证一个关键假设，完成并更新状态后再切换，避免并发检查改变多个变量或污染结论。

查询先从预聚合 Dashboard、有限时间窗和有限维度开始。扩大日志扫描、Trace 检索、profile 采集或依赖查询前先估算成本；可能造成高负载的查询属于变更类动作，必须显式授权。

## 假设管理与验证

假设应描述可验证机制，例如“版本 X 的超时配置使依赖 Y 的慢调用提前失败”，而不是“网络有问题”。按用户影响解释力、证据强度、检查风险和检查成本排序。

必须使用以下精确模板：

| 假设 | 支持证据 | 反证/缺口 | 下一检查 | 风险与成本 | 状态 |
|---|---|---|---|---|---|
|  |  |  |  |  | 待验证/支持/削弱/排除/已证实 |

一次只验证一个当前最高优先级假设。开始检查前说明它将产生什么可区分结果；检查完成后立即记录：

- 观察到的原始事实及时间范围；
- 事实如何支持或削弱该假设；
- 是否存在同样能解释现象的替代假设；
- 假设的新状态和下一项最小检查。

如果一个检查同时改变配置、容量和流量，就不能区分哪个变量产生效果。优先使用只读证据；必须干预时，将动作当作受控实验，限制单一变量、范围和时长，并经过止损授权门禁。

不得用以下证据单独确认根因：单条错误日志、单个慢 Trace、一次 CPU 峰值、一次 Pod 重启、第三方状态页、与事故相邻的发布，或止损后短暂好转。

## 止损决策与授权

止损的目标是限制用户影响，不是证明根因。优先选择范围小、可停止、可回滚、效果可观测的动作。每个动作独立评审和授权，不把多项高风险操作打包。

| 动作 | 授权人与授权时间 | 目标与范围 | 预期效果 | 风险与成本 | 前置条件 | 停止条件 | 回滚条件与方法 | 验证信号 | 状态 |
|---|---|---|---|---|---|---|---|---|---|
|  |  |  |  |  |  |  |  |  | 待授权/已授权/执行中/已停止/已回滚/完成 |

执行前必须满足：

1. 现场证据已按风险允许的程度保留。
2. 授权覆盖具体环境、对象、比例、时长和执行人。
3. 预期效果能由用户信号或系统信号在明确时间内观察。
4. 风险包括容量转移、数据丢失/重复、缓存击穿、依赖放大和恢复时间。
5. 停止条件说明何时立即中止，例如错误率恶化、数据异常或未在限定时间产生效果。
6. 回滚条件说明何时恢复原状态；回滚方法已验证可用，或明确其限制。

扩容可能把压力转移给依赖；重启可能丢失现场或制造连接风暴；`kill` 可能中断事务；清队列可能造成数据丢失；重放可能造成重复副作用；配置变更和流量切换可能扩大爆炸半径。没有相应授权、幂等性证据和停止/回滚条件，不执行这些动作。

动作后只观察预先指定的信号，达到停止条件就停止，达到回滚条件就回滚。没有预期效果也属于结果，应更新假设而不是连续叠加更多动作。

## 恢复验证与观察窗口

恢复验证同时比较异常前基线、异常窗口、动作后窗口和当前窗口。必须覆盖所有受影响范围，而不是只看已恢复的实例或地域。

| 信号 | 验证问题 | 示例判定方式 |
|---|---|---|
| 错误率 | 用户请求或任务是否恢复成功 | 回到事故前基线或既定 SLO 范围，错误类型不再集中增长 |
| 延迟 | P95/P99 和超时是否恢复 | 多个完整聚合周期内回到基线，尾延迟没有持续恶化 |
| 吞吐 | 正常工作量是否真正完成 | 输入、成功处理和业务完成量匹配当前流量，不以流量下降冒充恢复 |
| 饱和度 | 容量是否有稳定余量 | CPU、内存、连接、线程、磁盘或依赖限额低于已知风险边界 |
| 积压 | 延迟工作是否被消化 | 队列深度和最老消息年龄持续下降，处理速率高于输入速率 |
| 正确性 | 是否产生丢失、重复或错误结果 | 对账、幂等性、状态转换或关键业务抽样符合预期 |

观察窗口在事故开始时定义，并根据以下最长周期调整：告警评估周期、流量波峰、缓存/连接生命周期、队列排空时间、定时任务周期和依赖重试窗口。窗口必须覆盖多个完整采样周期；低流量系统还需等待足够样本量。任何关键指标反弹都重新进入分诊，不重置事实记录。

只有满足全部恢复标准并走完观察窗口，才能标记“已恢复”。止损仍在生效时最多标记“临时恢复”；永久修复已发布但观察不足时标记“恢复观察中”。

## 结论分级

事故结论使用以下术语，不能互相替代：

- **缓解**：用户影响下降，但服务未满足全部恢复标准，或影响仍可能扩大。
- **临时恢复**：当前已满足恢复标准和观察要求，但依赖临时止损、旁路、降级、扩容或人工操作维持。
- **直接原因**：紧邻用户症状并直接触发失败的技术机制，例如连接池等待导致请求超时；它不一定解释机制为何出现。
- **促成因素**：扩大事故概率、范围或恢复时间的条件，例如重试放大、容量余量不足、告警缺失或回滚缓慢。
- **根因**：被证据链证实、能够解释直接原因为何产生且排除了合理替代解释的底层原因。证据不足时必须写“根因未确认”。

永久修复、恢复和根因是三个不同状态。永久修复可能尚未验证，服务恢复也可能尚未找到根因；复盘不得为了结案而把最近的变更或最显眼的组件补写成根因。

## 证据不足时的输出

证据不足不是空白结论。停止扩大推断，使用以下结构交付：

### 已知

- 仅列可定位来源、时间窗口和口径的事实。
- 说明已确认的影响范围、当前状态和已排除项。

### 未知

- 列出阻止判断影响、直接原因或根因的具体缺口。
- 说明缺失数据是从未采集、已过期、不可访问，还是口径不一致。

### 最小下一检查

| 要验证的关键假设 | 最小只读检查 | 预期可区分结果 | 成本/风险 | 所需访问或授权 |
|---|---|---|---|---|
|  |  |  |  |  |

最小下一检查应缩小不确定性，而不是收集所有数据。若最小检查也需要高负载查询、配置变更、重启或其他写操作，先停在建议状态，列出授权需求、风险、停止和回滚条件。

## Runbook 与复盘

事故结束后更新 Runbook，使下一位响应者能够识别症状、执行低风险检查、申请止损并验证恢复。Runbook 至少包含：

- 入口条件、用户症状和对应 Dashboard/查询名称；
- 只读诊断顺序、预期结果和常见反证；
- 每项止损的授权角色、适用范围、风险、停止与回滚条件；
- 恢复标准、观察窗口和升级路径；
- 文档负责人、最近验证时间和定期演练要求。

复盘以时间线和证据为基础，明确区分缓解、临时恢复、直接原因、促成因素和已证实根因。行动项必须补齐四类缺口：

| 缺口 | 复盘问题 | 行动项示例 |
|---|---|---|
| 检测 | 为什么用户先于监控发现，或告警为何过晚/过噪 | 补充 SLI、调整告警窗口、明确通知和升级路径 |
| 诊断 | 哪项证据缺失、口径冲突或查询成本过高 | 补充结构化字段、有限基数指标、Trace 关联或安全查询 |
| 恢复 | 为什么止损、授权、执行或回滚耗时过长 | 验证回滚、预置审批路径、演练受控降级 |
| 预防 | 什么工程或流程措施能降低复发概率和影响 | 修复缺陷、增加容量边界、故障测试或变更保护 |

每个行动项应有负责人、优先级、截止时间、验收证据和复查状态。避免使用“加强关注”“优化监控”等不可验收表述；不以个人归责替代系统条件分析。

## 检查清单

- [ ] 影响范围、开始时间、当前状态、用户症状和恢复标准均已明确。
- [ ] 发布、配置、流量、依赖、资源、错误和响应动作已按同一时区进入时间线。
- [ ] 线上检查默认只读；Kubernetes 仅作为运行证据。
