## 通用关联诊断

以同一异常窗口、同一服务/实例和同一请求类型为边界，先画出请求时间线；用 trace ID 或 correlation ID 把入口延迟、依赖调用、重试、队列等待和下游处理串成证据链。没有时间对齐和传播一致的 correlation 字段时，只能陈述相关性，不能断言根因。

按以下层次定位，避免把所有等待都归到依赖服务：

1. **应用连接池**：池等待时间升高且在用连接接近上限，而服务端活跃连接、CPU 和延迟未同步上升，优先检查池容量、连接泄漏、长事务或请求并发。
2. **网络**：连接建立、DNS、TLS、超时或连接重置异常，多个调用方到同一目标路径同时受影响，而服务端处理时间稳定，指向网络路径或连接层。
3. **服务端饱和**：依赖端 CPU、内存、磁盘、线程/连接、队列深度与请求延迟在同一窗口上升，并能由 trace span 对齐，才支持饱和判断。
4. **数据或 partition 倾斜**：总体资源尚有余量，但少数 key、表/索引或 partition 的流量、延迟、积压显著偏高，说明热点被平均值掩盖。
5. **下游处理慢**：生产/发布稳定，积压和最老消息年龄增长，消费处理耗时或确认间隔同步升高；先定位消费者及其依赖，不把 broker 直接定为根因。

比较异常窗口与同环比基线，并至少交叉验证两类独立证据，例如应用 span 与服务端指标、积压年龄与消费速率。线上默认只读：采集指标、日志、trace 和元数据，不执行 kill、flush、purge、replay 或配置变更。

## MySQL

先将应用侧 MySQL span 的请求延迟拆成连接池等待、网络往返和服务端执行。连接池等待升高、池内活跃连接接近上限，但 MySQL 活跃连接和执行延迟稳定，说明瓶颈更靠近应用；两侧延迟同时上升才继续核对服务端资源与查询。

- **查询证据**：按 digest/模板观察 slow query 的次数、总耗时、P95/P99 和 `rows examined`；执行次数乘以单次成本比孤立慢样本更能解释请求影响。`rows examined` 激增可支持扫描放大或索引选择变化，但需与返回行数、执行计划和业务参数分布对照。
- **并发证据**：观察 `lock wait` 的等待数、等待时长、被阻塞事务和持锁事务时间线；deadlock 计数说明事务冲突发生，不等同于持续阻塞，需关联应用重试和失败率。
- **容量证据**：对齐活跃连接、线程运行数、CPU、buffer pool 命中、磁盘延迟和临时表等指标。仅连接数高不能证明饱和。
- **复制证据**：同时看复制延迟、relay/apply 队列、复制线程状态及只读请求所连节点；复制延迟只解释读到旧数据或只读节点滞后，不能自动解释主库请求变慢。

结论应明确受影响的查询模板、实例、时间段和请求占比，并指出证据更支持连接池、网络、服务端饱和还是数据倾斜。

## Redis

将客户端命令延迟分解为连接池等待、连接建立/网络和 Redis 执行时间。连接错误、超时或重置增加但服务端命令延迟稳定时，优先核对网络和客户端连接；服务端命令延迟、CPU、事件循环阻塞或内存压力同步异常时，再判断 Redis 侧影响。

- **访问效果**：分别观察 hit、miss 及请求量，计算 hit ratio 时保留分子分母；miss 增长还应与缓存策略、TTL、key 空间变化和回源压力对齐。
- **内存证据**：观察已用内存、maxmemory、eviction 速率和内存碎片比。eviction 表示发生逐出，但只有它与 miss、回源量和请求延迟同窗变化时，才支持用户影响链路；内存碎片高需结合 RSS 与分配器趋势判断。
- **热点证据**：按 key/命令分布识别 `hot key`，按 value 大小、序列化耗时和网络字节识别 `big key`。少数 key 的 QPS 或耗时显著偏离整体，属于数据倾斜，平均命令延迟可能看不出来。
- **回源证据**：把 miss、应用回源调用、数据库 QPS/延迟和最终请求错误放到同一 correlation 时间线，确认压力是否从 Redis 传导到下游。

## Kafka

生产侧观察 `producer error`、重试、超时、request latency 和发送速率，并按 broker、topic、partition 拆分；错误集中于连接建立而 broker request latency 稳定时，优先检查网络。broker CPU、磁盘、网络和请求队列与 request latency 同步上升，才支持服务端饱和。

- **积压证据**：`consumer lag` 是消息数量差，不是时间。必须同时观察最老消息年龄、生产速率、消费处理速率和消费组状态；lag 增长但最老消息年龄稳定，可能只是吞吐规模变化。
- **消费证据**：比较每秒生产与处理速率，并用消费 span 对齐拉取、业务处理、下游调用和提交 offset 的时间。处理速率低于生产速率且下游耗时上升，优先定位下游处理慢。
- **稳定性证据**：观察 `rebalance` 次数、持续时间、成员变化和消费暂停窗口。rebalance 与 lag 同窗并能解释暂停时长时才构成因果证据。
- **倾斜证据**：按 partition 比较输入速率、lag、最老消息年龄和消费耗时；少数 partition 持续偏高而整体 broker 有余量，说明 partition 倾斜或 key 分布热点。

## RabbitMQ

生产侧同时观察 publish 速率、失败、publish confirm 延迟和未确认发布；消费侧观察 deliver、ack 速率及二者差值。长期指标只按有预算的 vhost/queue/node 聚合，结合网络错误与 broker 资源区分连接层问题和服务端饱和。

- **队列状态**：`messages_ready` 表示等待投递，持续增长且 publish 高于 deliver，提示消费供给不足或路由集中；`messages_unacknowledged` 表示已投递未确认，增长且 deliver 尚可、ack 变慢，优先检查消费者处理或下游依赖。
- **消息年龄**：将最老 ready 消息年龄与队列数量一起看；数量相同可能对应完全不同的用户等待时间。
- **重投证据**：观察 redelivery 数量/比例、消费者重连、处理失败和 ack/nack 时间线。redelivery 增加可能来自消费者重启或确认超时，不能单独证明 broker 故障。
- **消费能力**：consumer utilization 下降时，对齐消费者数量、prefetch、deliver/ack 和单消息处理时长；若消费者忙于慢下游，扩大的 `messages_unacknowledged` 是结果而非 broker 根因。
- **连接证据**：connection/channel 只记录总数、创建/关闭速率、错误类别和达到限制事件；具体标识不得进入 metric label，只进入限时、采样、访问受控且有保留期的日志或 Trace。channel 多或连接数高只有在达到限制、资源同步升高或错误出现时才说明容量问题。

## 常见误判

- **单看平均值**：平均延迟会掩盖尾延迟、少数实例、key 或 partition；至少查看分位数、最大值、分组分布和受影响请求占比。
- **把 lag 数量等同延迟**：Kafka consumer lag 或 RabbitMQ 队列长度是数量；用户等待要由最老消息年龄、生产/处理速率和时间线证明。
- **把 hit ratio 下降直接认定 Redis 故障**：分母变化、TTL/访问模式变化或新 key 上线都会降低命中率；需看到命令异常、回源压力及用户影响的连续证据。
- **把慢 SQL 日志存在直接认定数据库是根因**：slow query 可能是长期基线、低频离群或上游取消后的结果；需证明其时间、调用链、次数和耗时足以覆盖本次异常。
- **把连接耗尽认定服务端饱和**：应用连接池满可能来自泄漏、长事务或本地并发，须与服务端活跃连接和资源交叉验证。
- **把积压认定 broker 故障**：生产正常而处理/ack 变慢时，积压通常指向消费者或其下游；broker 结论需要 broker 侧资源和请求指标支持。

## 检查清单

- [ ] 固定异常窗口、基线、服务/实例、请求类型和受影响比例。
- [ ] 验证 trace ID/correlation ID 在入口、依赖调用、消息头和消费者中的传播，并建立请求时间线。
- [ ] 分离连接池等待、DNS/连接/TLS/网络、服务端执行和重试耗时。
- [ ] 核对服务端 CPU、内存、磁盘、连接/线程、请求队列是否与延迟同窗变化。
- [ ] 按查询、key、topic/queue、partition、实例和消费者分组，排查数据或 partition 倾斜。
- [ ] 同时比较生产/发布、deliver/消费、处理、ack/commit 速率以及最老消息年龄。
- [ ] 用至少两类独立证据支持结论，并记录不能排除的替代解释。
- [ ] 保持线上只读；任何 kill、flush、purge、replay 或配置变更都应退出诊断流程，另行评审和授权。
