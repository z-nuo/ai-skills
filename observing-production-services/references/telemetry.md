# Telemetry 设计

## 用户结果与信号

SLI 从实际业务完成点定义 good/valid events、分母、阈值和窗口；异步流程不能只看入口成功。低流量兼看绝对失败数和较长窗口，数据缺失单列，不能当零错误。

请求用 RED（速率、错误、延迟），有限资源用 USE（利用、等待饱和、错误）。面板沿用户结果 → 服务 → 依赖 → 实例下钻，统一时间/过滤并标发布；资源升高只是待解释的证据。

## 日志与指标

日志使用稳定 event、服务/版本、规范 operation、outcome、错误分类和必要 trace/correlation 字段。处理或改变结果的边界记录一次异常，保留必要异常链，避免逐层重复。

counter 按 reset-aware 增量/rate，gauge 说明当前值与上限，时长/大小用单位明确的 histogram。bucket 围绕 SLO，聚合组保持兼容；不要平均实例 p95/p99。counter `_total`、seconds/bytes 等沿用现有命名。

label 仅留会改变查询/告警的有限维度，估算组合基数；ID、SQL、原始 URL、时间戳和错误正文不作 label。诊断细节仅进必要且受控的日志/trace，凭据、Cookie、私钥和完整敏感载荷不采集。

## Trace 与采样

span 放在入口、依赖、消息及真实业务阶段，不逐函数打点。同步传播标准 context，baggage 仅有限必要字段；batch/合并等多来源可用 links，消息排队与处理分开计时。

head sampling 不知道最终结果，tail sampling 可优先保留错误、慢请求和关键路径，但有缓冲/等待成本；定义预算、丢弃计数及降级。采样 trace 不替代完整 SLI 计数，审计记录不依赖普通诊断采样。

## 告警与管道

告警面向用户症状、SLO burn rate、容量耗尽或人工需处理的积压；使用合适的快慢窗口及低流量分母。给出阈值依据、持续时间、处理动作和 Runbook，不为每条异常建告警。

SDK/exporter 与业务隔离，队列、重试、资源及本地缓冲有界；监测接收/丢弃、导出延迟和最后成功时间。空图区分零值、无流量、查询错误与缺失。跨主机记录时钟偏差，duration 尽量用单进程 monotonic clock。

按实际量控制序列、日志字节、span 与保留期；脱敏覆盖正文、属性和失败缓冲，采集故障不能拖垮业务。
