# 数据一致性设计

从业务不变量、数据所有者和失败恢复出发，确定事实来源、冲突规则及允许的不一致窗口。能用本地事务解决就不升级为分布式方案。

1. 读取实际 schema、读写链路、缓存和 producer/consumer，标出事务及跨系统边界。
2. 对关键步骤间的失败说明残留状态、检测与恢复，覆盖超时但成功、重复、乱序和进程退出。
3. 按真实缺口选择事务、Outbox/Inbox、补偿或对账；不默认生成全套 DDL、消息框架、任务和业务实现。
4. 用实际失败窗口验证方案；评审先报告可能丢失、重复或长期不一致的具体路径。

- 缓存失效、TTL 与租约：[Redis](references/redis.md)。

- 跨系统发布、补偿和修复：[一致性模式](references/patterns.md)。

跨服务异步流程同时核对消息与恢复模式。数据库与消息分别成功不等于整体原子成功；默认考虑重复投递与消费幂等。分布式锁不能替代事务或唯一约束，补偿也是可能失败的新业务动作。

交付与问题相称的正常/失败路径、必要契约和恢复方式；关键事实缺失时限定结论，不将方案设计写成已验证。
