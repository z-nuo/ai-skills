## 核心目标

从业务不变量和失败恢复出发，设计跨 MySQL、Redis、消息队列和服务边界的数据流。先明确哪些状态必须正确、允许多长时间不一致，再选择事务、缓存和消息模式。

## 核心原则

- 为每类数据指定唯一事实来源和所有者，缓存、索引和消息都是派生状态。
- 能在一个本地事务内解决的问题，不升级为分布式一致性问题。
- 跨系统默认按 at-least-once 投递和幂等处理设计，不宣称端到端 exactly-once。
- 每个异步步骤都必须可检测、可重试、可补偿或可人工修复。
- 一致性方案必须包含失败矩阵、观测、对账和恢复，不只描述正常流程。

## 工作流

### 1. 检查现状

阅读 schema、migration、Repository、Redis key、消息 schema、producer/consumer、重试配置、定时任务和监控。识别当前数据所有者、调用方、历史兼容行为及已有工具。

缺少会改变一致性模型的信息时，每次只询问一个阻塞问题；其余信息使用显式假设继续。

### 2. 定义业务不变量

用可验证句子描述绝不能发生的状态，例如“同一支付请求最多产生一笔有效扣款”。同时定义：

- 哪些状态要求立即一致，哪些允许最终一致。
- 可接受的不一致窗口和业务影响。
- 冲突时哪个系统的值获胜。
- 哪些操作可重试，哪些副作用不可逆。

### 3. 明确所有权与事务边界

标出每个服务拥有的数据、事实来源、同一 MySQL 事务内的写入，以及跨 Redis、消息或其他服务的边界。禁止让两个服务直接共同拥有同一业务记录。

### 4. 绘制流程和失败矩阵

按顺序列出业务写入、缓存更新或失效、消息持久化、发布、消费和派生写入。对每个相邻步骤之间的失败建立矩阵：

| 步骤/失败点 | 可能残留状态 | 如何检测 | 自动恢复 | 补偿/人工处理 |
|---|---|---|---|---|

覆盖超时但实际成功、重复执行、乱序、进程崩溃、网络分区、依赖不可用和永久毒消息。

### 5. 加载相关规则

- MySQL 事务、锁和本地 Outbox 写入读取 [references/mysql.md](references/mysql.md)。
- Redis 缓存、TTL 和锁边界读取 [references/redis.md](references/redis.md)。
- Kafka/RabbitMQ 投递、确认、重试和顺序读取 [references/messaging.md](references/messaging.md)。
- Outbox、Inbox、Saga、补偿和对账读取 [references/patterns.md](references/patterns.md)。

只加载流程实际涉及的中间件。跨服务异步流程必须同时读取消息和模式参考。

### 6. 选择恢复模式

优先选择简单、可运营的模式：本地事务保证核心写入；Transactional Outbox 连接数据库与消息；Inbox/唯一约束实现幂等消费；Saga 处理跨服务业务补偿；定期对账修复长期漂移。

分布式锁不能替代数据库约束、幂等键或事务。只有明确锁资源、租约、续期、所有权验证和 fencing token 后才采用。

### 7. 生成契约草案

默认输出必要的 MySQL DDL、Redis key/TTL/失效策略、消息 envelope、幂等键、排序键、重试/死信和对账任务草案。除非用户要求，不直接生成 Go/PHP 业务实现。

消息 schema 或公共接口需要重新设计时，**REQUIRED SUB-SKILL:** Use designing-microservice-interfaces。

### 8. 设计观测和验证

先写出值班人员需要回答的问题，再配置结构化事件、指标和告警。至少考虑 Outbox 最老待发布时间、发布失败、consumer lag、重复/幂等命中、重试、死信、对账差异和修复失败。

指标 label 使用有限集合，禁止使用用户 ID、事件 ID 或完整错误文本。日志/trace 使用 correlation ID、event ID 和业务键关联，但不得记录密钥、token 或完整敏感载荷。

需要实现测试时，**REQUIRED SUB-SKILL:** Use testing-backend-services，覆盖事务回滚、重复、乱序、崩溃窗口、重试、补偿和对账幂等性。

## 任务模式

- **新流程设计**：从不变量推导事务、缓存、消息及恢复方案。
- **现有方案评审**：先按严重程度列出可能丢失、重复、乱序或永久不一致的路径，并定位到具体步骤。
- **故障后加固**：根据实际时间线找出未被检测或恢复的窗口，补充约束、观测、修复和回归测试。

## 默认交付物

按以下顺序输出：

1. **业务不变量与一致性目标**：事实来源、允许延迟和冲突规则。
2. **所有权与事务边界**：服务、数据及同步/异步边界。
3. **读写与消息流程**：正常路径和状态转换。
4. **失败矩阵**：残留状态、检测、重试、补偿和人工处理。
5. **数据与消息契约**：DDL、Redis key、消息 envelope、幂等和排序规则。
6. **恢复与对账**：重试、死信、Saga、补偿、扫描和修复策略。
7. **观测与告警**：问题、结构化事件、有限基数指标、阈值依据和 runbook。
8. **测试与回滚**：故障注入点、验证命令、发布停止条件和恢复路径。
9. **未决问题**：只保留会改变一致性模型的决策。

评审模式将发现的问题置于最前；没有明确不变量或消费者范围时，不给出“方案安全”的结论。

## 红线

- 不采用“先写数据库，再直接发消息”并忽略进程崩溃窗口。
- 不把 Redis 视为核心业务事实来源，除非业务明确以 Redis 为权威存储。
- 不依赖固定延迟、消息只投递一次或消费者永不并发等假设。
- 不无限重试永久错误，不建立没有重放和负责人流程的死信队列。
- 不把 compensation 描述成数据库 rollback；补偿是新的业务动作，也可能失败。
- 不用高基数指标或敏感日志换取可观测性。
