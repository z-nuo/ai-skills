# Redis：缓存与锁

## 缓存契约

每类缓存明确事实来源、key 维度、TTL、允许陈旧窗口、失效和重建方式。业务未明确指定时，Redis 缓存不是权威记录。

- 数据库提交后失效缓存，失效失败按现有重试、事件或对账恢复。
- 并发旧读可能在失效后回填旧值；按一致性要求选择版本、再次失效、有界 TTL 或绕过缓存。延迟双删不保证严格一致。
- 区分不存在、空结果和下游失败；失败不能作为正常空值缓存。负缓存、TTL 抖动和热点请求合并须符合业务允许的陈旧与等待边界。
- Redis Lua 只对对应 Redis 执行范围原子，不跨 MySQL。多 key 操作还须确认集群 slot 等约束。

## 分布式锁

仅在确需互斥的资源上使用锁，明确 key、owner token、租约及过期后的行为；释放时原子核对 owner，不能无条件删除别人的锁。

续租失败或进程暂停可能使旧持有者继续写。需要阻止过期持有者时，由写入端验证 fencing token 或使用版本条件写。锁不替代数据库事务、唯一约束和业务幂等。

验证旧读回填、失效失败、空值/失败、租约过期和旧持有者写入等实际风险；不要以“更稳妥”为由给每次读取加锁或增加兜底路径。
