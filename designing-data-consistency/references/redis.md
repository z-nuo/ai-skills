## 定位事实来源

默认 MySQL/业务服务是事实来源，Redis 是可丢弃并重建的派生状态。每类 key 必须定义 owner、格式、TTL、数据版本、失效触发和重建方式。

只有业务明确以 Redis 数据结构为权威存储时，才设计持久化、复制、故障转移和恢复不变量；不要因为访问快就默认它是事实来源。

## Cache Aside 读路径

典型 Cache Aside：

1. 读取 cache。
2. miss 时读取事实来源。
3. 写入带 TTL 的 cache。
4. 返回结果。

必须处理“旧读回填”：写事务提交并删除 cache 后，较早的 miss 查询可能把旧值重新写回。根据一致性要求选择：

- cache value 携带单调版本，只允许较新版本覆盖。
- 通过变更事件再次失效，并由对账扫描修复漏失效。
- 对极短不一致窗口使用有界 TTL；明确窗口而不是称其强一致。
- 对强一致读取绕过 cache 或读取事实来源。

“延迟双删”只能缩小某些竞态窗口，不是严格一致性证明；固定延迟无法覆盖所有慢查询和调度情况。

## 写入与失效

- 先提交 MySQL 事务，再删除或更新 Redis；不能让回滚事务留下新 cache。
- 默认删除 cache 而不是同时更新多个派生形态，除非更新逻辑集中且可证明原子。
- cache 删除失败必须有重试、变更事件或对账兜底，并监控失效积压。
- key 包含 schema/version 前缀，格式变更时可并行迁移和整体退役旧 namespace。
- 多 key 原子更新可用 Lua，但 Lua 只保证 Redis 内原子性，不能与 MySQL 形成共同事务。

## TTL 与缓存保护

- TTL 根据可接受陈旧窗口、访问模式和重建成本确定，不使用统一拍脑袋值。
- 批量 key 增加有限随机 jitter，避免同一时刻过期形成缓存雪崩。
- 缓存空结果可缓解穿透，但使用较短 TTL，并区分“确实不存在”和下游失败。
- 热点 miss 使用 singleflight/请求合并、逻辑过期或有界锁防止缓存击穿。
- 限制 value 大小和集合基数，避免一次重建或序列化拖垮服务。
- 监控 hit/miss、load latency、重建失败、过期、驱逐和事实来源回源压力。

## 分布式锁边界

Redis 锁只用于减少并发工作，不能替代数据库唯一约束和幂等：

- 使用随机 owner token，并在 Lua 中校验 token 后释放。
- 租约必须有界；长任务明确续期、取消和进程暂停后的行为。
- 锁过期后旧持有者仍可能继续工作，需要下游接受单调 fencing token 拒绝过期写入。
- 获取失败、续期失败和 Redis failover 都必须有明确处理，不能假设互斥永不失效。
- 如果受保护资源不支持 fencing 或条件写，不声称锁提供严格互斥安全。

## 评审清单

- Redis 是否明确为派生状态，事实来源和 owner 是否唯一？
- 写事务提交与 cache 失效顺序是否正确？
- 旧读回填、删除失败和消息丢失是否有恢复路径？
- TTL、jitter、空值缓存和热点保护是否基于业务窗口？
- key schema、数据版本和 namespace 迁移是否可控？
- 分布式锁是否具有 owner token、租约和 fencing token？
