## 选择顺序

按不变量需要逐层增加机制：

1. 单库内用本地事务、条件更新和唯一约束。
2. 数据库写入后需要可靠发消息时使用 Transactional Outbox。
3. 消费者会修改本地数据库或触发副作用时使用 Inbox/业务幂等键。
4. 多服务必须完成一组可撤销业务步骤时使用 Saga。
5. 所有异步流程最终使用对账发现遗漏、长期失败和人工操作造成的漂移。

模式不能替代业务不变量。先明确事实来源、成功定义、不一致窗口及不可逆动作，再选择组合。

## Transactional Outbox

Transactional Outbox 将业务写入和待发布事件放在同一数据库本地事务中：

1. 接收具有幂等键的业务命令。
2. 在一个事务中更新业务表并插入 Outbox。
3. commit 后由独立 publisher 扫描待发布事件。
4. broker confirm 成功后标记已发布。
5. consumer 使用 Inbox 或业务唯一约束处理重复消息。

它关闭“数据库已提交但进程在发消息前崩溃”的丢失窗口，但不消除重复：broker 已接收而 publisher 尚未标记时崩溃，恢复后会再次发布同一 `event_id`。

发布实现选择：

- **轮询表**：简单、可控，需监控扫描延迟、索引和 backlog。
- **CDC/binlog**：延迟低且减少轮询，但增加基础设施、schema 映射和恢复复杂度。

两者都必须保持稳定 event ID、可重放证据和发布进度观测。不能在 publisher 标记成功前删除事件；归档/清理策略必须晚于排障和重放保留期。

## Inbox 与幂等消费

消费者在本地数据库建立 Inbox 去重表：

```sql
CREATE TABLE consumer_inbox (
    consumer_name VARCHAR(128) NOT NULL,
    event_id CHAR(36) NOT NULL,
    payload_hash CHAR(64) NOT NULL,
    processed_at DATETIME(6) NOT NULL,
    PRIMARY KEY (consumer_name, event_id)
) ENGINE=InnoDB;
```

处理流程：

1. 开启本地事务。
2. 插入 `(consumer_name, event_id, payload_hash)`。
3. 唯一约束冲突时读取旧 hash；相同则视为已成功，不同则告警。
4. 首次插入时执行本地业务写入。
5. Inbox 与业务写入一起 commit。
6. commit 成功后才 ack/commit 消息进度。

如果副作用是远程 API，Inbox 与远程调用无法原子提交。优先使用下游幂等键；否则把待调用动作写入本地任务表，由 worker 重试并通过查询/对账确认结果。

Inbox 清理期必须覆盖 broker 保留、重试、死信和人工重放窗口。业务层具有更自然唯一键时，例如 `(payment_provider, charge_request_id)`，同时保留业务唯一约束作为最终防线。

## Saga

Saga 把跨服务长事务拆为多个本地事务，并为已完成步骤定义后续补偿。它提供业务级最终一致性，不提供数据库隔离；其他请求可能看见中间状态。

两种协调方式：

| 模式 | 适用 | 风险 |
|---|---|---|
| 编排 orchestration | 步骤多、分支多、需要统一超时和状态可见性 | 编排器成为关键组件，需高可用和幂等 |
| 协同 choreography | 流程短、事件关系稳定、服务自治要求高 | 隐式耦合、循环依赖和排障困难 |

Saga 状态必须持久化，至少包含 saga ID、业务键、当前状态、已完成步骤、下一动作、attempt、deadline 和 last error。状态转换使用条件更新或版本列，避免并发 worker 重复推进。

对每一步定义：

- 前置条件和本地不变量。
- 命令/事件幂等键。
- 成功结果及可查询证据。
- 超时是失败、未知还是仍在执行。
- 可重试错误与最大时限。
- 补偿动作、负责人和停止条件。

不可逆动作尽量后置。例如先预留库存和授权支付，确认订单后再扣减/捕获；通知类副作用放在核心状态确定之后。

## 补偿设计

补偿是一个新的业务动作，不是数据库 rollback。原动作可能已被外部观察，补偿也可能超时、重复或失败。

- 补偿必须幂等，使用 saga ID + step 作为幂等键。
- 按业务依赖通常逆序执行，但需根据实际不变量判断。
- 记录原动作证据和补偿结果，不能只改 Saga 状态。
- 支持“补偿中”“补偿失败”“需人工处理”等持久状态。
- 并发业务变化可能使直接还原旧值错误；使用反向业务操作，例如释放预留，而不是覆盖当前库存。
- 外部返回超时时先查询真实结果，再决定重试原动作或补偿，避免双重副作用。

某些动作不可完全补偿，例如已发送邮件或已被用户消费的权益。方案必须描述残余影响、客服/人工流程和审计，而不是声称恢复到从未发生。

## 对账与修复

对账比较事实来源与派生状态，发现在线重试没有覆盖的长期漂移。每个关键异步流程至少定义：

- 扫描范围：时间窗口、状态、分片和水位线。
- 比较键：业务 ID、外部单号、event ID、金额及版本。
- 差异类型：缺失、多余、状态不符、金额不符、卡住超时。
- 修复动作：重发事件、重建缓存、重新推进、补偿或人工审核。
- 幂等性：重复扫描和重复修复不得产生新副作用。
- 限流与隔离：避免修复任务压垮在线系统。
- 审计：记录发现证据、决策、执行版本、操作者和结果。

优先从事实来源重建派生数据。涉及资金、库存或不可逆副作用时，不自动“取较新值覆盖”，先定义权威规则和人工阈值。

对账指标包含扫描延迟、扫描数量、差异数量/年龄、自动修复成功率、人工积压和重复出现率。重复差异说明在线流程仍有系统性缺口，不能只扩大修复频率。

## 订单流程示例

订单创建、缓存和下游履约可组合如下：

1. API 以 `request_id` 幂等创建订单；订单行和 `order.created` Outbox 在同一 MySQL 事务提交。
2. commit 后删除订单查询 cache；删除失败由变更事件/重试和对账兜底。
3. publisher 将稳定 `event_id` 发布到以 `order_id` 分区/路由的消息流。
4. 库存 consumer 使用 Inbox 去重，在本地事务创建库存预留并发布结果事件。
5. 支付和库存步骤由 Saga 推进；超时先查询下游真实结果。
6. 任一步永久失败时，对已完成步骤执行幂等补偿，例如释放库存预留。
7. 对账任务扫描长时间中间态订单、Outbox backlog、缺失消费结果和外部支付差异。

该流程允许短暂中间状态，但必须保证不会因重复消息重复扣款、不会因 publisher 崩溃永久漏发，并能发现乱序、补偿失败和长期漂移。

## 失败矩阵模板

逐个分析相邻持久化/确认步骤之间的崩溃窗口：

| 步骤/失败点 | 可能残留状态 | 检测证据 | 自动恢复 | 补偿/人工处理 |
|---|---|---|---|---|
| 业务写入前失败 | 无业务记录、无 Outbox | 请求日志/幂等记录 | 客户端用同一幂等键重试 | 无 |
| 业务与 Outbox commit 后、返回前崩溃 | 已成功但调用方未知 | 幂等记录、业务行 | 重试返回原结果 | 冲突时人工审核 |
| broker 接收后、Outbox 标记前崩溃 | 消息可能重复 | broker/event ID、未标记 Outbox | publisher 重发，consumer 去重 | 重复副作用进入审计 |
| consumer 业务 commit 后、ack 前崩溃 | 消息重新投递 | Inbox、业务结果 | Inbox 命中后 ack | hash 冲突隔离 |
| Saga 步骤超时 | 成功与否未知 | 下游查询、correlation ID | 查询后重试/推进 | 无法确认则人工处理 |
| 补偿永久失败 | 部分业务效果残留 | Saga 状态、告警 | 有界重试 | 专属队列和负责人 |
| cache 失效失败 | Redis 仍为旧值 | 版本、失效积压、抽样对账 | 重试删除/重建 | 强一致读取绕过 cache |
| 对账修复中断 | 部分差异已修复 | repair ID、水位线、审计表 | 幂等续跑 | 失败项隔离 |

实际方案继续加入网络超时但实际成功、重复、乱序、依赖降级、schema 不兼容、broker/数据库不可用和人工误操作。每一行都必须能回答“谁在多久内看到并处理”。

## 评审清单

- 本地事务是否已经覆盖能原子完成的全部动作？
- Transactional Outbox 是否与业务数据同事务，publisher 崩溃是否允许安全重发？
- Inbox/业务唯一约束是否和业务写同事务，保留期是否覆盖重放窗口？
- Saga 是否持久化状态、步骤幂等、超时可查询且不可逆动作后置？
- 每个补偿是否作为可失败的新业务动作被观测和重试？
- 对账是否有事实来源、扫描水位、幂等修复、限流、审计和负责人？
- 失败矩阵是否覆盖成功但未知、重复、乱序和永久失败？
