# 消息：投递、确认与重放

## 共同边界

按重复可能发生设计消费。发送成功、broker 确认和业务处理完成是不同阶段；Kafka 事务也不自动覆盖外部数据库或 HTTP 副作用。

- 需要去重时使用稳定 `event_id`，重试与重放保留原 ID；类型、版本、实体键和关联字段按实际契约设置，不默认生成完整 envelope。
- 消费幂等记录与业务写入尽量同事务，副作用完成后才 ack/commit。去重保留期覆盖 broker 保留、延迟重试、死信及人工重放窗口。
- 顺序以实际实体/partition 为界；版本快照可拒绝旧版本，增量事件则须去重和有序处理，不能简单丢弃所有旧 sequence。
- 瞬时错误有界退避，永久错误隔离并保留修复证据；死信须有处理责任与重放方法，避免无限 requeue 热循环。

## Kafka

幂等 producer 防止的重复范围与业务幂等分开。异步或批量处理只能提交连续已完成的安全 offset，不能越过未完成项。

rebalance 撤销时停止接收对应 partition 新工作，有界收束 in-flight，未完成记录不提交。重试 topic 可能改变同实体顺序，按业务决定是否允许。

## RabbitMQ

按可靠性要求同时检查队列持久化/副本、消息持久化、publisher confirm 和不可路由消息的 return/mandatory 处理；confirm 不证明消费者完成。

prefetch 限制实际 in-flight，ack 使用原 delivery 所属 channel。批量确认不能覆盖失败或未完成 delivery。

## 重放

先修永久错误，保留原业务标识与幂等规则，限定目标、速率和停止条件。验证重复、乱序、业务成功后确认前崩溃及部分失败；重放后以最终业务记录对账，不只看队列清空。
