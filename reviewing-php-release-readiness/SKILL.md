# PHP 发布就绪审查

先说明当前补丁是否存在源码层阻断，再说明部署条件与未验证的生产依赖。审查只读；用户明确要求修复时才修改对应问题。

## 1. 重新建立基线

每次“更新后重新检查”都重新读取 branch、HEAD、暂存、未暂存、未跟踪文件和当前调用方，旧报告只作为核对线索：

```bash
git status --short --branch
git rev-parse HEAD
git diff --stat
git diff --name-only
git diff --cached --stat
git diff --cached --name-only
git ls-files --others --exclude-standard
```

随后读取完整相关 diff 和新文件。默认“当前未提交修改”包括暂存与未暂存；用户指定提交或分支时先确认比较基线。混合暂存状态还要确认实际发布的是暂存快照还是整个工作树，不能将两者等同。

保留原有工作树修改；比较旧版上下文与新路径，区分本次新增问题、已有问题及已修复问题。删除或废弃逻辑时核对调用、路由、配置、模板、CLI/worker 与跨仓库消费者，不能只用语法通过判定闭环。

## 2. 依变更选择验证

读取 [验证方法与发布边界](references/verification.md)，按实际风险执行：

- 所有修改的 PHP：匹配目标 PHP 版本的 lint 和差异检查。
- 注释/格式：对正确的两个快照比较 token，检查注释参与反射、注解或行号的特殊语义。
- 业务变化：追踪输入、错误、持久化、副作用、并发和恢复，选择现有隔离测试或可用集成验证。
- Composer/协议变化：比对声明、lock、安装版本与调用方字段/方法；兄弟包 HEAD 不证明调用服务已安装。
- 长驻进程、队列或缓存：列出实际需要的部署、重启/回收与缓存更新条件。

`tests/` 下的脚本先核对副作用，不能直接运行可能扣款、发奖、写真实 Redis 或调用生产 RPC 的脚本。未运行项注明原因；测试替身只证明对应隔离范围。

## 3. 给出可操作的结论

发现按严重程度排序，每项提供当前文件/行号、触发条件、具体后果及最小修正，并标明新增还是已有。重复检查时确认旧问题在当前源码中是否仍然成立。

没有发现源码阻断时可写“当前补丁源码层可进入发布流程”，并列出验证证据、待满足的部署条件与线上未验证项。存在阻断时明确指出；证据不足以确认关键行为时写明缺口，不以含糊的“建议谨慎”代替结论。已有问题是否阻断本次发布取决于其是否仍在发布路径上，不因它是历史问题而忽略影响。

审查结论绑定当前基线与实际验证范围。QConf、Redis、RPC、支付、奖励、队列、流量或生产部署没有验证时明确说明，不声称已完成生产验收。
