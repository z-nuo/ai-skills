# clarifying-before-solving 设计规格

## 背景

复杂或模糊的问题常因目标、约束、上下文或成功标准缺失而得到看似完整但偏离真实需求的答案。新 Skill 用逐次访谈补齐高价值信息，在形成方案前校准需求，同时避免对简单明确的问题增加无意义的交互成本。

## 已确认决策

- Skill 名称为 `clarifying-before-solving`。
- 仅在问题复杂、模糊或信息不足时进入追问流程；简单且明确的问题直接回答。
- 每轮只提出一个问题，并根据用户最新回答选择下一项最高价值问题。
- 当 AI 判断已掌握至少 95% 的决策相关信息时，用一句简洁陈述复述需求与目标，请用户确认。
- 用户确认后才给出最终方案；用户修正理解时继续逐次追问。
- 用户明确要求“不要再问，直接给方案”时立即停止追问，基于现有信息回答，并显式列出会影响结论的关键假设与不确定性。

## 方案选择

采用自适应追问状态机，不采用固定问卷或仅靠宽泛原则的自由追问。

固定问卷虽然稳定，但容易询问与当前任务无关的信息。自由追问文件更短，但不同 AI 对“95%”的解释差异较大。自适应状态机通过可观察的进入、继续和退出条件约束行为，同时允许问题随任务变化。

## 文件结构

```text
clarifying-before-solving/
├── SKILL.md
└── agents/
    └── openai.yaml
```

`SKILL.md` 保存触发判断、访谈循环、充分度检查、确认和退出规则。`agents/openai.yaml` 提供展示名称、简短描述和默认调用提示词。该 Skill 不需要脚本、reference 或 assets。

## 行为流程

### 1. 判断是否进入访谈

满足任一条件时进入访谈：存在多个会显著改变方案的合理解释；缺少目标、受众、范围、约束、现状或成功标准；任务包含高影响或难以撤销的决策；用户明确要求先澄清需求。

当请求简单、具体、低风险，且已有信息足以产生基本唯一的正确输出时，直接回答。

### 2. 逐次追问

每轮识别“其不同答案最可能改变最终方案”的未知项，只问一个简短问题。优先使用互斥的选项并说明差异；开放问题仅用于无法合理枚举选项时。收到回答后重新评估，而不是预先执行固定问题清单。

不得在同一消息中合并多个问题，不得把建议伪装成问题，也不得在信息仍不足时提前输出完整方案。

### 3. 判断 95% 信息充分度

“95%”是决策充分度门槛，不是数学概率。只有以下各项均已明确或具有不会改变主方案的安全默认值时，才视为达到门槛：

- 真实目标和期望结果。
- 使用者、受众或受影响对象。
- 当前背景、已有条件和问题边界。
- 必须遵守的约束与明确排除项。
- 可用于比较方案的成功标准和优先级。
- 会显著改变架构、成本、风险或交付物的关键偏好。

未知细节若只影响实现微调，可作为显式假设留到方案中；若可能改变推荐方向，则必须继续追问。

### 4. 确认理解

达到充分度门槛后，用一句简洁陈述概括用户的目标、关键约束和成功标准，然后只询问用户是否确认。用户确认后输出最终方案；用户纠正或补充时，更新理解并继续一次一个问题的循环。

### 5. 用户提前退出

用户明确要求直接回答时立即退出访谈。最终回答先列出关键假设和剩余未知项，再给出当前信息下的最佳方案。不得用“还没达到 95%”拒绝用户的退出指令。

## 默认交付行为

访谈阶段的每次回复只包含：必要的一句上下文，以及一个问题。确认阶段只包含需求复述和一个确认问题。最终方案的结构由原任务决定，不强制套用固定模板。

## 发现与界面元数据

frontmatter 的 `description` 聚焦触发场景：需求模糊、存在多种解释、关键约束缺失、高影响决策或用户要求在作答前澄清。它不描述完整流程，避免代理只读取元数据而跳过正文。

`agents/openai.yaml` 包含：

- `display_name`: `先澄清，再解决`
- `short_description`: `在提出最终方案前逐步澄清复杂、模糊或信息不足的真实需求`
- `default_prompt`: `使用 $clarifying-before-solving 在提出方案前逐步澄清我的真实需求。`

## 验证策略

先在没有该 Skill 的情况下运行压力场景，确认代理会提前给方案、一次提出多个问题或忽略退出指令，并记录实际失败。创建 Skill 后重复相同场景，验证：

1. 模糊需求只产生一个最高价值问题，不产生完整方案。
2. 后续问题确实依赖用户上一轮回答。
3. 简单明确的问题直接回答，不机械追问。
4. 信息充分后先复述需求并等待确认。
5. 用户要求直接回答时停止追问，并标明假设和不确定性。
6. 用户否认复述内容时回到逐次追问，而不是继续输出方案。

静态验证覆盖目录命名、YAML frontmatter、`agents/openai.yaml`、占位符、相对链接、字数和官方 `quick_validate.py`。行为验证使用新上下文，避免测试代理从设计文档或预期答案中获得提示。

## 完成标准

- 触发条件能区分模糊复杂请求与简单明确请求。
- 访谈阶段任何一轮都只有一个问题。
- 95% 门槛由决策相关信息清单支撑，不依赖空泛自信判断。
- 正常路径必须先获得需求复述确认，再输出最终方案。
- 用户提前退出始终优先，并得到带假设的当前最佳方案。
- Skill 和界面元数据通过结构校验，行为场景达到预期。

## 中文化修订

### 目标

将 Skill 的用户界面和代理指导完整本地化为自然、明确的简体中文，不改变触发条件、状态转换、95% 信息门槛、确认流程或提前退出规则。

### 翻译范围

- 将 `SKILL.md` frontmatter 中的 `description` 翻译为中文。
- 将 `SKILL.md` 的标题、章节、规则、列表、状态表和常见错误全部翻译为中文。
- 将 `agents/openai.yaml` 的 `display_name`、`short_description` 和 `default_prompt` 全部翻译为中文。
- 保持目录名 `clarifying-before-solving`、frontmatter 的 `name`、调用标识 `$clarifying-before-solving` 和 YAML 字段名不变。

### 翻译原则

采用语义本地化，不做生硬逐句直译。使用命令式、可执行的表达，保持“一次只问一个问题”等约束的强度。中文文本不得引入新的触发场景、例外或输出模板，也不得删除现有的简单问题直答、需求确认和用户提前退出行为。
