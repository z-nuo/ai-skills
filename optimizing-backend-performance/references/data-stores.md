## 数据层实验契约

数据库或缓存出现慢查询、高 CPU、高内存、连接等待或命中率变化，只能生成待验证假设，不能直接宣布根因。先把用户可见路径拆成应用排队、连接池等待、网络、服务端排队与执行、锁等待、结果传输与解码，以及 Redis miss 后的回源；再用处于同一时间窗口的 trace、客户端指标和服务端指标定位主要贡献。

生产环境默认只读取已有指标、trace、日志、query digest、历史慢日志和已批准的采样结果。不连接未经明确授权的服务，不临时开启高开销采集，不执行全量 keyspace 遍历，不在生产运行压测。需要主动补证时，先记录授权、目标假设、目标实例、最大范围、时限、资源和业务停止阈值、数据处理要求及恢复动作。

每个候选优化先固定：

1. 性能目标：端到端 p95/p99、正确完成吞吐、错误率和单位工作资源成本。
2. workload：查询或命令比例、读写比、数据规模与分布、热点、返回大小、缓存冷热、并发或到达率。
3. 不变量：唯一性、外键、事务隔离、原子性、幂等、顺序、read-after-write、缓存 freshness 和持久化语义。
4. 基线与反证：当前证据、预期可区分结果、不可接受结果和未覆盖的不确定性。
5. 控制：相同版本、schema、配置、数据集、预热判据、运行阶段和观测方式，一次只改变一个关键变量。
6. 停止与回滚：延迟、错误、timeout、内存、CPU、连接、复制或数据正确性任一越界即停止，并恢复原 schema、配置或发布版本。

性能数字只有在同一契约下通过正确性检查才可比较。通过删除校验、忽略失败、改变 key 含义、延长允许陈旧窗口，或绕开唯一性、事务、幂等和一致性得到的数字，不是可接受的性能优化。

## MySQL 端到端归因

### 先分解时间

将一次数据库 logical operation 至少分成以下阶段，并在同一 trace 或可对齐的时间窗口中关联：

| 阶段 | 可用证据 | 常见混淆 |
|---|---|---|
| 应用队列与连接池等待 | acquire duration、wait count、in-use/idle、acquire timeout | 总 SQL span 可能把拿连接前的等待包含进去 |
| 建连与网络 | DNS、dial、TLS、socket read/write、连接复用 | 网络等待不能由服务端执行时间反推 |
| 服务端接入与执行 | query digest、执行时间、CPU、I/O、buffer pool、临时表、排序 | 慢 SQL 与请求变慢同时发生不等于它贡献最大 |
| lock wait | 等待事务、持有事务、锁对象、等待时间、deadlock | 长事务可能在应用空闲或网络等待期间继续持锁 |
| 结果读取与应用解码 | rows returned、结果字节、fetch/decode span、客户端 CPU | 服务端很快仍可能因大结果集使端到端变慢 |

先比较这些阶段的绝对耗时和 p99 贡献，再选下一条证据。不得因为慢日志存在记录，就跳过连接池等待、网络、锁和结果读取而宣布根因。

### 选择候选查询

按规范化 query digest 聚合，而不是只挑单条最长样本。候选集至少同时检查：

- 调用频率、总耗时、平均与尾部耗时，以及对目标 endpoint 或 job 的覆盖比例。
- `rows examined`、rows returned 及两者比值；比值高是扫描放大线索，不自动等于缺索引。
- 创建内存或磁盘临时表、filesort、读取字节、写入字节和返回结果大小。
- `lock wait`、deadlock、事务持续时间及等待链。
- 数据量、列基数、选择性、倾斜、热点值、NULL 比例和参数分布。
- 错误、timeout、取消、重试与失败查询的耗时；不能只分析成功样本。

慢查询日志和 statement digest 都可能包含敏感 schema、SQL 或参数信息。优先使用规范化 digest，限制访问和保留期；开启或提高采样前评估 I/O、CPU、日志量和脱敏风险。样本阈值会漏掉大量中等耗时但高频的查询，因此还要看总耗时和频率。

## MySQL 查询与计划证据

### `EXPLAIN` 与 `EXPLAIN ANALYZE`

- `EXPLAIN` 用优化器估算描述访问路径，本身不证明实际行数、循环数或耗时。优先在本地、测试环境使用；生产只读使用也必须经过授权，限定语句、实例、timeout 和观察窗口，并考虑优化开销及 metadata lock。
- `EXPLAIN ANALYZE` 会实际执行语句并返回实际 iterator timing、rows 和 loops。默认只在受控环境和安全数据集运行；不得把它当成生产只读探针，也不得对可能产生副作用、资源消耗不可控或返回规模未知的语句尝试运行。
- 对生产捕获的 SQL，先去除或替换敏感 literal，在与生产版本、schema、统计信息和代表性数据分布一致的隔离副本复现。参数差异可能改变计划，不能只测一个最有利值。
- 记录计划中的 access type、候选与实际 key、key parts、估算与实际 rows、loops、filter、排序、临时表和 iterator 时间。估算偏差用于提出统计信息或数据倾斜假设，不是立即刷新统计或强制 plan 的授权。

计划实验必须与端到端指标相连。即使扫描行数下降，也要验证 wall time、CPU、I/O、返回行数、连接占用时间、p99、错误率和并发下的吞吐；冷、热 buffer pool 分开记录，不能用热缓存单轮结果外推生产。

### 锁与事务证据

使用既有 `performance_schema`、`sys` 视图、事务日志和 trace 构建等待关系：谁在等待、谁持有、锁定对象、事务开始时间、最后语句、影响请求和等待持续时间。`SHOW ENGINE INNODB STATUS` 是瞬时且范围较宽的诊断输出，只在获准实例限次读取，并对输出按敏感数据处理。

不要只优化等待方 SQL。检查持锁事务是否包含网络调用、用户交互、无界批量工作、结果处理或不必要的空闲时间；区分 row lock、metadata lock、死锁回滚、I/O 慢导致持锁延长，以及应用连接池耗尽。终止连接或事务属于有业务副作用的恢复操作，不是性能诊断步骤，必须由事故流程单独授权。

## MySQL 索引和查询形态实验

### 索引候选

索引变更前列出查询谓词、join、排序、分组、返回列和真实参数分布，再评估：

- 选择性与数据倾斜。低选择性单列可能没有收益，组合条件的联合分布不能由单列基数相乘替代。
- 复合索引顺序。用等值、范围、排序和覆盖需求解释顺序，并验证所有重要 query shape，而不是只服务一个样本。
- 覆盖收益。减少回表可能换来更宽索引、更多 buffer pool 占用和更高写成本。
- 写放大与存储。测量 INSERT/UPDATE/DELETE 延迟、redo/undo、页分裂、索引大小、备份和复制影响。
- 唯一性、外键和事务不变量。唯一索引与外键索引具有正确性职责，不得因“重复”而删除；用非唯一索引替换唯一索引不等价。

在影子 schema、隔离副本或代表性测试库创建候选索引，使用相同数据规模与分布对比计划和 workload。在线 DDL 仍可能消耗 I/O、CPU、临时空间、复制带宽并产生 metadata lock；生产变更必须有兼容性核对、空间余量、限速与停止阈值、部署窗口和经过演练的回滚路径。删除旧索引前要观察完整业务周期并确认没有不可见的低频消费者。

### 查询与批处理候选

| 候选 | 必须验证的性能边界 | 必须保持的语义 |
|---|---|---|
| 消除 `N+1` | 父项数量分布、查询次数、总返回字节、join/IN 列表规模、数据库 CPU 与 p99 | 缺失行、重复行、排序、权限过滤和 snapshot/事务可见性一致 |
| 减少过量字段 | 行宽、网络字节、解码 CPU、覆盖索引可能性 | 所有调用方字段契约和审计字段仍满足 |
| 分页方式调整 | 深页分布、扫描行数、排序成本、并发写下的稳定性 | continuation key、去重、漏读和排序 tie-breaker 明确定义 |
| 批量写 | batch 大小分布、单批耗时、redo、锁、峰值内存和复制延迟 | 原子范围、部分失败、重试幂等、错误定位和唯一性不变 |
| 缩短事务 | 持锁时间、往返次数、冲突率和 p99 | 业务原子性、隔离级别、读写顺序与失败回滚不变 |
| 连接复用与 prepared statement | 建连成本、statement cache、服务端资源和长尾参数 | session 状态被正确重置，租户、权限、时区和事务不串用 |

这些候选都必须在代表性数据规模、参数分布、并发和冷/热状态下验证。更少 SQL 次数并不保证更快；一个巨大 join、IN 列表或 batch 可能增加锁范围、内存峰值、尾延迟和失败重试成本。

## MySQL 锁、事务与连接池

连接池是队列和容量边界，不是越大越快。扩大前先确认 acquire 等待显著，且数据库、proxy、网络和存储仍有容量。记录每实例池上限及所有实例总和，并预留管理、迁移、failover 和其他客户端连接预算。

连接池实验至少观察：

- 应用 acquire wait 分布、timeout、in-use、idle、等待队列和请求公平性。
- 数据库连接上限、当前连接、活跃线程、CPU、内存、I/O、lock wait 和事务时长。
- 建连速率、连接 lifetime/idle 回收、健康检查、DNS/failover 和 TLS 成本。
- 端到端吞吐、p99、错误率、timeout/cancel、重试放大和下游饱和度。

一次只改变 pool size、idle size、lifetime 或 acquire timeout 中一个关键变量。扩大连接池可能把应用排队移动到 MySQL 线程、锁或磁盘队列，并在故障时形成连接风暴。采用有界并发、带抖动的退避和全局连接预算；timeout 失败必须进入错误率，不能通过无限等待或无限重试隐藏。

事务连接归还前必须完成 commit/rollback 并清理 session 状态。任何优化后都验证事务隔离、deadlock 重试边界、幂等键、唯一约束和未知提交结果；不得用缩短事务的名义拆开必须原子的写入。

## Redis 端到端归因

Redis 命令很快不代表客户端请求很快。将一次 logical operation 关联到以下阶段：

| 阶段 | 观察项 |
|---|---|
| 应用与连接池 | acquire wait、pool saturation、event-loop backlog、序列化、客户端 CPU、timeout 和重试 |
| 网络与协议 | DNS/dial/TLS、连接复用、round trip、请求/响应字节、socket backpressure |
| Redis 执行 | 命令耗时、命令复杂度、吞吐、CPU、blocked clients、keyspace 与数据结构基数 |
| 内存与后台活动 | used memory、RSS、fragmentation、allocator、fork/COW、复制、持久化、eviction |
| 缓存结果 | hit/miss、TTL、freshness、negative cache、失效传播、回源 QPS/延迟/错误 |

把客户端等待、Redis CPU/内存和回源压力放在同一时间线。hit rate 下降可能是 workload 或 TTL 变化；Redis 延迟上升可能来自 big key、网络、fork、内存压力或客户端 head-of-line blocking。任一单项都只能生成假设。

## Redis 诊断命令安全契约

先从已有 dashboards、应用 trace、客户端 metrics、代理统计和历史采样取证。确需命令补证时，只使用已授权目标，优先单个隔离实例或脱敏副本，逐条执行并记录起止时间。以下是本文允许考虑的 Redis 诊断命令；每一行同时规定复杂度、范围、停止条件和替代方案。

| 诊断命令 | 复杂度与观测成本 | 允许范围 | 停止条件 | 更安全替代 |
|---|---|---|---|---|
| `INFO <section>` | 近似 O(1)，输出与所选 section 的指标数有关；频繁轮询增加主线程与网络工作 | 一次只读所需 section，低频、限时、单实例 | 命令延迟、实例 CPU、网络或采集量越过预设阈值立即停止 | 读取现有监控 exporter、历史 dashboard |
| `SLOWLOG LEN` | O(1)，只返回当前条数 | 单实例、单次读取 | 出现 timeout、连接排队或业务错误上升即停止 | 现有 slowlog 指标或应用 trace |
| `SLOWLOG GET 128` | O(N)，N 为返回条目数；可能暴露命令参数与 key | 固定小 count，单实例、短窗口，结果脱敏和限期保留 | 达到 128 条、时间预算、数据量上限或资源阈值即停止 | 规范化应用 trace、代理侧命令摘要 |
| `LATENCY LATEST` | 近似 O(1)，只读已启用 latency monitor 的最新事件 | 单实例、单次读取；不得为此临时改生产配置 | 无已采样事件即结束，不扩大范围或开启采集 | 现有 Redis latency metrics、客户端分段 trace |
| `MEMORY USAGE <key> SAMPLES 5` | 对嵌套类型，`SAMPLES 5` 是固定样本估算，不是完整结构的精确内存；完整验证使用 `MEMORY USAGE <key> SAMPLES 0`，它会遍历全部嵌套元素，成本 O(N) | `SAMPLES 5` 只查已由采样定位、获准且脱敏的少量 key；`SAMPLES 0` 仅限可销毁的离线副本或隔离实例 | 估算达到 key 数、返回字节、时间或 p99/CPU 阈值即停止；完整测量先核对实例可销毁和资源预算，超限时终止隔离实例 | 应用写入时记录 value size histogram；先以逻辑大小找候选，再离线完整测量 |
| `OBJECT FREQ <key>` | O(1)，仅在 LFU 策略下有意义，计数是近似值 | 只查有限候选 key，不枚举 keyspace | 达到候选数或观测预算即停止 | 应用/代理侧按哈希 key 的有界频率采样 |
| `SCAN <cursor> MATCH <pattern> COUNT 200` | 单次调用摊销 O(1)，完成一轮 O(N)；`COUNT` 是提示而非硬上限，结果可能重复 | 禁止生产大 keyspace 无界迭代；仅批准的有限 shard/DB、时间窗与最大返回量 | cursor 归零，或先达到最大调用数、key 数、时限、CPU/p99 阈值；任一即停 | 元数据索引、写入侧抽样、脱敏副本或备份离线分析 |
| `redis-cli --bigkeys -i 0.1` | 基于扫描，完整运行 O(N)；`redis-cli --bigkeys` 对集合类型主要报告逻辑基数或长度候选，不是实际内存字节排名 | 仅隔离副本或经批准的小 keyspace；生产大 keyspace 禁止全程运行 | 达到时限、扫描比例、key 数、CPU、延迟或复制延迟阈值即中止客户端 | 先用它找候选，再在隔离副本完整测量物理内存；也可在写入侧记录逻辑大小 |
| `redis-cli --hotkeys -i 0.1` | 基于扫描，完整运行 O(N)；依赖 LFU 近似频率，不能代表精确请求率 | 仅启用 LFU 且获准的小 keyspace 或隔离副本 | 达到时限、扫描比例、key 数、CPU 或延迟阈值即中止客户端 | 应用 trace、proxy/client 有界采样、按哈希 key 聚合 |
| `KEYS <pattern>` | O(N) 且在主线程遍历整个 keyspace；`KEYS` 一旦发送会在 Redis 主线程执行完，断开客户端通常不能取消服务端工作 | 生产环境禁止；仅可在可销毁离线实例和已知微小数据集使用 | 采用纯前置门禁：keyspace 未知或超过预设阈值就不发送；命令开始后不宣称可中止，资源或时限超限时终止隔离实例并重建 | 有界 `SCAN`、元数据索引、脱敏副本 |
| `MONITOR` | 额外工作随全实例命令吞吐增长，可能显著降吞吐并暴露完整命令和敏感数据 | 生产默认禁止；仅空闲隔离环境、严格秒级窗口和已知低流量 | 达到固定秒数、事件数、字节数或任一资源阈值立即断开 | 应用 trace、SLOWLOG、有界采样或代理摘要 |

`SLOWLOG` 记录的是 Redis 处理命令的服务端执行时间，不包含客户端排队、网络传输和响应读取；阈值以下命令也不会出现。它适合定位候选命令，不能单独解释端到端 p99。不要为补齐证据而在线修改 slowlog、latency monitor 或 maxmemory 配置；配置变化本身属于需审批、可回滚的实验。

安全扫描必须有硬边界：目标 shard/DB、最大调用数、最大检查 key 数、最大返回字节、固定时限、命令间隔和业务资源阈值。cursor 未归零但任何预算先耗尽时仍必须停止，并把覆盖率和遗漏写入报告。不得把游标扫描包装成“非阻塞”后无限运行；也不得并行扫全部 shard。

生产大 keyspace 禁止使用 `KEYS` 或无界扫描；pattern 看似很窄也不构成例外。

## Redis hot key、big key 与内存

### 识别 hot key

优先使用应用 trace、代理或客户端有界采样，按不可逆哈希后的 key 标识聚合请求次数、并发、请求/响应字节、command type、hit/miss 和耗时。限制聚合基数和保留期，避免泄露租户、账号、token 或业务 payload。

hot key 是 workload 分布事实，不只是某个频率计数。把候选 key 与 shard CPU、网络、单线程排队、客户端连接利用率和回源关联，并区分：

- 单个 key 请求率高。
- 单次操作的数据结构成员多或复杂度高。
- value 大导致网络、序列化和 allocator 成本高。
- miss、过期或 eviction 使请求集中回源。

分片、副本读取、本地缓存或请求合并都可能改变一致性、read-after-write、故障切换和公平性。只有在所有者、失效方式、允许陈旧窗口与 fallback 容量明确后才进入实验。

### 识别 big key 与内存压力

分开记录逻辑大小与物理内存。逻辑大小包括 string 长度，hash/set/zset/list/stream 的成员数、元素大小分布和单次响应字节；物理内存包括 key/value 编码、allocator 开销及实例的 fragmentation、RSS、used memory 和峰值内存。成员数、字符串长度、响应字节和固定样本估算都不能当作精确物理内存字节排名。一个成员很多但编码紧凑的 key 与少量超大元素的 key，风险不同。

先用安全采样或 `redis-cli --bigkeys` 的逻辑基数/长度结果定位候选，不能把该输出解释为实际内存字节排名。对候选使用固定 `SAMPLES 5` 只能得到嵌套类型的估算；需要确认完整物理内存时，在可销毁的离线副本或隔离实例使用 `SAMPLES 0` 遍历全部嵌套元素，并按 O(N) 成本设置前置资源预算。不要在生产大 keyspace 逐 key 取大小。检查删除、过期、序列化、复制、迁移和恢复成本；大 key 可能使看似 O(1) 的删除产生释放开销，也可能让 pipeline 的响应缓冲形成内存峰值。

内存优化不得只看 used memory：

- 压缩会增加客户端 CPU、尾延迟和失败处理复杂度，必须在代表性 value 分布上测量压缩比与 p99。
- 拆 key 会增加命令数、网络往返和部分成功状态，必须定义原子边界、版本与清理方式。
- 改 TTL 或 eviction policy 会改变 freshness、miss 和回源压力，属于语义与容量实验。
- 删除字段、记录或校验以缩小 value 会改变数据契约，不是性能优化。

## Redis 客户端、pipeline 与缓存实验

### 连接与客户端行为

先确认等待发生在 pool acquire、单连接 head-of-line blocking、event loop、socket write/read、DNS/dial/TLS、服务端还是回源。客户端指标至少覆盖 active/idle/waiter、acquire timeout、连接建立率、重连、in-flight、请求/响应字节、命令 p99 和错误分类。

扩大连接池前检查 Redis `maxclients`、所有应用实例连接总和、文件描述符、proxy 限额、TLS/内存成本和 failover 预算。更多连接可能增加服务端公平性问题和故障时重连风暴。一次只改变 pool size、per-connection in-flight、idle/lifetime 或 timeout 中一个变量，并保留有界并发、指数退避加抖动和全局预算。

### pipeline 与批处理

pipeline 减少 round trip，但不会降低命令本身的服务端复杂度。按真实 command mix 和 value 大小比较 batch size，并报告每个 logical operation 与每批的指标：吞吐、p50/p99、排队时间、响应总字节、客户端/服务端峰值内存、CPU、错误、timeout、连接占用和其他租户公平性。

批次必须有最大命令数、最大字节和最大等待时间。验证响应与请求一一对应、部分失败可见、重试不会重复副作用、取消不会留下无界工作，并保留事务或 Lua 原本要求的原子语义。不得把失败批次中的成功项全部重放；若无法判断单项结果，先定义幂等键和对账恢复。

批量命令也要按实际元素数和返回大小评估命令复杂度。吞吐上升但 p99、内存峰值、错误率或公平性越过阈值时，候选失败并回滚 batch 参数。

### 本地缓存、TTL 与回源

本地缓存或更长 TTL 会减少 Redis 请求，但可能扩大缓存陈旧窗口和每实例内存。实验前定义事实来源、允许 freshness、read-after-write、negative cache、失效消息丢失后的恢复和版本冲突规则。验证 warm/cold、稳定命中、集中失效、节点扩容和故障恢复阶段。

同时测量 Redis hit/miss、应用本地 hit/miss、eviction、过期速率、回源 QPS/p99/错误、请求合并等待和源站连接池。单飞或请求合并要有等待者上限、timeout、错误传播和取消规则；不能通过返回过期数据或吞掉回源错误制造命中率和延迟改善。

为 TTL 加随机抖动、预热或 stale-while-revalidate 前，先确认业务允许的陈旧边界。缓存击穿、雪崩和失效风暴实验只在隔离环境或模拟器中进行，不能在生产主动批量过期。任何方案都必须保留幂等、唯一性、一致性和回滚能力。

## 验证、停止和回滚

MySQL 与 Redis 候选使用同一验收框架：

| 维度 | 基线和候选都必须报告 |
|---|---|
| 用户结果 | offered/completed logical operations、成功、业务错误、系统错误、timeout、cancel、未完成 |
| 性能 | 正确完成吞吐、p50/p95/p99、阶段耗时、排队和重试放大 |
| MySQL | query 次数、rows examined/returned、计划、临时表/排序、lock wait、连接池与数据库饱和度 |
| Redis | command 次数与分布、客户端等待、CPU、内存、eviction、hit/miss、hot/big key 证据和回源压力 |
| 正确性 | 唯一性、事务、原子性、幂等、重复/丢失/乱序、缓存 freshness、部分失败与对账 |
| 成本 | CPU、内存、I/O、网络、连接、存储、复制、恢复时间和运营复杂度 |

每轮采用预先选择的固定时长或固定 offered operation 数，并记录独立重复、运行顺序、原始数据和环境差异。出现错误率或 timeout 恶化、数据不变量失败、MySQL 锁/复制/连接超限、Redis p99/内存/eviction/回源超限，或任何未预期副作用时立即停止。

回滚不是一句“恢复配置”。索引变更要有兼容查询与 schema 回退顺序；连接池和 batch 参数保留旧值及逐步回退；缓存变更要能区分新旧 key/version，并处理双读写或失效残留；本地缓存要有关闭开关和回源容量保护。回滚后重新验证服务健康、错误率、连接、复制、缓存 freshness 和数据对账，再形成结论。

只有重复的受控实验在正确性、错误率和资源边界内达到预先定义的业务阈值，才能把候选称为已证实改善。只有线上只读观察、单个计划、一次采样或相关性时，结论保持“待验证”，并写明下一步最小安全实验。
