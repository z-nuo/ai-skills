## 性能目标与业务不变量

先把 SLO 或业务目标写成可判定的验收条件，再选择工具和优化方案。每个条件都要包含指标、阈值、适用范围、观察窗口和 workload；只写“更快”或“降低资源”不可验收。

| 维度 | 验收条件应回答 | 示例形式 |
|---|---|---|
| 延迟 | 哪条路径、哪个 percentile、阈值和窗口是什么 | 峰值订单创建请求的 p99 小于目标阈值 |
| 吞吐 | 正确完成的请求或消息速率是多少 | 在目标到达率下保持稳定完成速率且无持续积压 |
| 错误率 | 哪些 logical operation 计入分母，timeout、cancel、降级如何归类 | 用户可见 outcome 以 offered logical operations 为分母，attempts 单独报告 |
| 资源成本 | 每单位有效工作允许多少 CPU、内存、I/O 或费用 | 报告 CPU-seconds/request、峰值 RSS 和实例数 |

性能目标必须与正确性条件同时成立。实验前声明不可破坏的业务不变量，至少检查：

- 鉴权与授权判定不被绕过或缓存为错误主体。
- 幂等键的作用域、有效期和重复请求结果保持一致。
- 需要保证的事件、事务或写入顺序不被重排。
- 唯一性约束在并发、重试和故障恢复下仍成立。
- 持久化确认、事务提交和消息投递语义没有弱化。

关闭校验、隐藏错误、降低持久化级别或改变交付语义得到的数字不属于性能提升。生产环境默认只读取已有指标、trace、日志、历史 profile 和压测报告；任何主动补证必须另行授权并满足安全边界。

## 代表性 workload

workload 是实验输入契约，而不是一个平均 QPS。基线和候选方案必须使用同一契约；若契约变化，结果属于不同实验。

| 字段 | 必须记录的内容 |
|---|---|
| 请求或消息分布 | 各 endpoint、operation、topic、消息类型的比例及分层结果 |
| payload | 大小分布、关键字段基数、压缩状态和异常大对象比例 |
| 读写比 | 读、写、更新、删除、事务及 cache hit/miss 的比例 |
| 数据规模 | 行数、key 数、partition 数、索引规模、热点和倾斜分布 |
| 负载模型 | 并发数或到达率；说明 closed model 或 open model，不能混为一谈 |
| 缓存状态 | cold、warm、命中率目标、预填充方式和失效策略 |
| 依赖延迟 | 数据库、cache、broker 和外部 API 的延迟/错误分布及限额 |
| 峰值形态 | 日常稳态、阶跃、突发幅度与持续时间、恢复或积压回放方式 |

说明 workload 代表哪个业务窗口，并以生产流量分布、脱敏回放或业务预测作为依据。合成 workload 无法覆盖的长尾 payload、热点 key、慢依赖或重试流量要列为不确定性。不得用与真实系统不同的轻量请求组合外推端到端收益。

## 受控基线与运行阶段

每份基线记录以下上下文，缺少会影响结果的字段时不得标记为可比较：

- 代码、runtime、依赖、schema 和镜像版本。
- 应用、数据库、cache、broker、内核和 feature flag 配置。
- 服务实例、proxy、replica、partition、consumer 及可用区拓扑。
- CPU 型号、核数、内存、磁盘、网络，以及容器 request/limit 和 throttling。
- 数据集版本、规模、分布、缓存状态和准备步骤。
- 预热完成判据、预先停止规则、offered/completed 数、有效样本、重复次数和运行顺序。
- 指标、trace、profile 或日志的采样配置与观测开销。
- 可复现命令、原始结果位置、时间戳和同时发生的部署或后台任务。

同一次运行要按系统状态切段，不混合不同阶段比较：

1. **cold start**：进程、JIT/OPcache、连接池、page cache 或应用 cache 尚未稳定。
2. **warm-up**：持续加载直到吞吐、延迟、连接数、cache hit rate 和 runtime 行为达到预设稳定判据。
3. **steady state**：输入和关键资源在容许波动内，可用于主要前后比较。
4. **saturation**：负载继续增加后，队列、尾延迟、错误或资源等待持续增长。
5. **recovery**：突发或故障结束后，队列、积压、延迟和资源回到稳态的过程。

若目标是 cold start 或 recovery，就分别比较相同阶段，并单独定义验收条件。warm-up 不能用固定等待时间替代稳定判据；若只能按时间预热，记录原因并把残余漂移列入不确定性。

## 指标与 percentile 聚合

先分离三套计数，不能把重试当作新的用户请求：

- **offered logical operations**：负载模型计划并实际发出的用户可见业务操作，每个业务操作只计一次。
- **completed logical operations**：观察窗口内得到终态 outcome 的 logical operation，不论结果为成功、显式错误、timeout 或 cancel。
- **attempts**：初次调用及其所有 retry 的实际尝试次数。用 attempts 计算 retry amplification，例如 `attempts / offered logical operations`，并同时报告 completion coverage。

用户可见成功率和按 outcome 分类的错误率都以 offered logical operations 为分母；成功、业务错误、系统错误、timeout、cancel 和窗口结束时尚未完成的 operation 分列，使各类计数可与分母对账。若 cancel 明确由调用方主动放弃，可单列而不归因于服务错误，但不得从 logical operation 分母删除。

每轮同时报告 offered/completed logical operations、attempts、按分类的成功/错误率、吞吐、p50/p95/p99、CPU、内存和饱和度。饱和度包括 queue depth、连接池等待、CPU throttling、磁盘利用率、broker lag 或其他受限资源的等待信号。按问题补充 allocation、GC、锁等待、I/O、下游延迟和成本，但不能替代基本指标。

延迟必须声明测量的是 logical operation 还是单次 attempt，并按 success、error、timeout、cancel 等 outcome 分层。若目标是用户收到终态的时间，timeout/cancel 事件时刻可作为该用户可见 outcome 的延迟；若目标是原操作本可完成的服务时间，这些观测属于 right-censored，只知道删失边界，不能当作精确完成延迟。指标系统若把超量程样本截到固定上界或 `+Inf` bucket，须报告截断/上界规则和样本数，不得把上界值当作真实样本值。

percentile 必须来自同一事件总体：

- 优先保留原始样本或可合并的 histogram。
- 对单调 counter 形式的 histogram bucket，先按 counter reset-aware 规则转换为对齐、非重叠窗口的增量；counter reset、实例重启或缺失窗口必须显式处理，不能直接用窗口首尾值相减后保留负数。
- 只有 label、事件总体、单位、过滤条件、对齐窗口和 bucket 边界相同时，才逐 bucket 汇总增量并计算整体 percentile；用于区分实例的 label 可在确认其余 label 一致后聚合掉。
- 记录 bucket 分辨率。目标阈值落入过宽 bucket、`+Inf` bucket 或样本集中在少数 bucket 时，将 percentile/阈值判断标为不确定，并调整 bucket 或保留原始样本后重测。
- 不平均各实例、各窗口或各轮预计算的 p95、p99；percentile 的算术平均没有总体分位数含义。
- bucket 不兼容时分别报告，或回到原始样本重算；无法重算则明确不可聚合。
- 检查负载生成器是否记录排队时间并避免 coordinated omission；若未覆盖，说明其对尾延迟的低估。

请求数和错误分类用于解释 percentile 是否被样本排除改变。timeout、客户端取消、限流、重试耗尽和降级结果不得从分母中静默删除。

## 假设、反证与实验优先级

每个瓶颈写成可证伪的因果假设，并把已测事实、解释和未知项分开：

| 假设 | 已知事实 | 支持证据 | 反证或缺口 | 下一实验 | 预期可区分结果 | 收益/风险/成本 |
|---|---|---|---|---|---|---|
| 若某等待是瓶颈，改变其容量将改善目标指标 | 原始观测 | 与假设一致的指标、trace 或 profile | 冲突证据及尚未测量项 | 最小单变量实验 | 成立与不成立时分别应出现的信号 | 预期收益、正确性风险、采集和变更成本 |

优先验证预期收益高、正确性和生产风险低、执行成本小，并且有清晰反证条件的假设。相关性只用于生成假设：CPU、GC、慢查询或 lag 与延迟同向变化，不自动证明它们是原因。没有预期可区分结果的实验先补设计，不进入执行。

## 单一变量实验

实验前冻结 workload、offered load、环境、数据集、版本、预热、阶段切分、观测方式、统计方法和预先停止规则，一次只改变一个关键变量。执行顺序如下：

1. 写明因果假设、目标指标、正确性守恒条件和反证。
2. 规定成功、失败、资源停止阈值和回滚条件。
3. 随机化或交错 baseline/candidate 运行顺序，降低时间漂移影响。
4. 每轮选择固定时长或固定 offered logical operation 数作为停止规则，不同时强制 achieved sample count 和运行时长相同；各方案使用同一种规则，并记录 offered、completed 和有效样本数。
5. 检查条件是否漂移，再做统计比较和正确性比较。

有些变更必须联动，例如 schema 与查询、producer 与 consumer 协议。此时明确组合原因，把组合实验视为一个候选方案，并增加可行的拆分实验或 ablation，以辨别各部分贡献。若无法拆分，只能把因果结论限定到整个组合，不能归因于其中一个参数。

生产环境不执行未授权压测、故障注入或高开销 profiling。线上问题先用只读证据缩小假设，再在隔离环境、脱敏回放或经批准的最小范围中验证。

## 前后统计比较

不要只给最佳一轮或单个百分比。先声明指标方向：`signed change = candidate - baseline` 保留变化符号；improvement 按业务方向定义，延迟/错误率/成本等越低越好时用 `baseline - candidate`，吞吐等越高越好时用 `candidate - baseline`。每个核心指标同时报告：

- baseline 与 candidate 的绝对值及单位。
- signed change、按指标方向定义的 improvement 和相对变化，并写明计算式；baseline 为 0 时不计算百分比，只报告绝对变化或有业务语义且分母有效的 ratio。
- 每轮结果、重复运行的中位数或均值，以及分布、方差、标准差或置信范围。
- 请求数、有效样本数、错误率和运行持续时间。

重复次数、分析单位、区间方法和置信水平在实验前确定。独立运行或预先定义的随机化 block 是分析单位，不能把同一轮内相关的请求当作独立重复。交错 baseline/candidate 时，在同一 block 内计算配对变化量，再从各 block 的配对变化量估计 effect interval。根据依赖结构使用 run-level bootstrap、cluster/block bootstrap 或 time-series bootstrap；长尾或分布不对称时优先保留分布，不以大请求数掩盖只有少量独立运行。

每轮 percentile 的分布用于描述运行间变异，不等于合并全部兼容事件得到的 pooled percentile；两者回答不同问题，应分别命名和报告，不能相互替代。对多个指标或多个方案反复筛选时说明多重比较风险，不从偶然最佳值选择结论。

相对变化必须与绝对值一起解释：低基数上的巨大百分比可能没有业务意义，微小百分比在高流量下也可能有显著成本。统计差异还必须通过预先定义的业务阈值，才能称为有用改善。

比较前逐项核对版本、配置、拓扑、硬件限额、数据集、workload、阶段、采样开销和统计口径。只要关键环境不可比，就停止计算“提升百分比”或因果归因，只报告各自观察、已知差异和不确定性，并提出恢复可比性的下一实验。

## 正确性守恒

性能结果通过后仍需独立通过正确性守恒检查：

| 检查项 | 要验证的结果 |
|---|---|
| 错误分类 | 业务错误、系统错误、限流、降级和取消没有被重新归类或隐藏 |
| timeout | 客户端、服务端和依赖 timeout 数量、阶段及最终结果完整记录 |
| 重试 | 尝试次数、重试放大、退避和最终失败进入统计 |
| 重复 | 幂等键、重复消息和重复写入结果符合业务不变量 |
| 丢失 | 请求、消息、写入和确认可对账，没有静默丢弃 |
| 乱序 | 需要保序的 key、partition、事务或事件顺序保持 |
| 缓存陈旧 | freshness、TTL、失效传播和 read-after-write 条件达标 |
| 数据不变量 | 鉴权、唯一性、约束、事务、持久化和投递语义保持 |

使用业务计数、校验和、对账、影子结果或隔离环境的差分测试验证，而不只检查 HTTP status 或进程未崩溃。正确性证据缺失、错误率恶化或资源越过安全上限时，候选方案失败，即使延迟或吞吐更好。

## 结论强度

结论必须与证据强度匹配：

| 级别 | 使用条件 | 允许的表述 |
|---|---|---|
| 已证实 | 可比环境、重复受控实验、正确性通过，变化量 effect interval 支持预先声明的方向并达到业务阈值 | 在已定义范围和 workload 下，该变量导致达到阈值的改善，并报告区间和适用边界 |
| 强支持 | 多类证据一致且受控实验支持，但仍有明确限制或样本不足 | 证据强支持该假设，同时列出限制和下一验证 |
| 待验证 | 仅有相关性、单轮结果、观测证据或关键数据缺失 | 当前观察与假设一致，不能声称因果或提升 |
| 已排除 | 实验有足够辨别力，effect interval 排除预先定义的最小有意义效应，或出现明确反证 | 在本实验范围内排除达到该效应的假设，并保留适用边界 |

结论注明适用的版本、环境、workload 和阶段。辨别力不足、effect interval 仍包含最小有意义效应，或只有“未观察到差异”时归为待验证，不得写成已排除或“证明完全相同”。不得把 microbenchmark 外推为端到端提升，不得用相关性替代因果。环境或统计口径不可比时，最高只能标记为待验证。

## 执行记录模板

每次实验至少留下以下记录，未填写项要说明为何未知：

```text
性能目标：指标 / 阈值 / 范围 / 观察窗口
业务不变量：鉴权 / 幂等 / 顺序 / 唯一性 / 持久化
workload：分布 / payload / 读写比 / 数据规模 / 并发或到达率 / 冷热 / 依赖 / 峰值
环境：版本 / 配置 / 拓扑 / 硬件或容器限额 / 数据集
阶段：cold start / warm-up 判据 / steady state / saturation / recovery
基线：命令 / 停止规则（固定时长或固定 offered logical operation 数）/ 重复次数 / 观测开销 / 原始结果
假设：事实 / 支持证据 / 反证 / 下一实验 / 预期可区分结果
控制：单一变量 / 固定条件 / 顺序 / 停止条件 / 回滚
结果：offered/completed logical operations / attempts / outcome / retry amplification / 吞吐 / p50 / p95 / p99 / CPU / 内存 / 饱和度
比较：分析单位 / 配对变化量 / signed change / improvement / 绝对值 / 相对变化 / effect interval / 置信水平 / 不确定性
正确性：timeout / 重试 / 重复 / 丢失 / 乱序 / 缓存陈旧 / 数据不变量
结论：已证实 / 强支持 / 待验证 / 已排除 / 适用边界
```
